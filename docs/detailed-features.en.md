## Getting started, in full

**Windows, no install (recommended)**

1. Download `MediaDownloader-1.4.0-portable.zip` from [Releases](https://github.com/QingYan1012/media-downloader-web/releases/latest).
2. Unpack it to a path with no non-ASCII characters and no spaces, and not under `C:\Program Files`.
3. Double-click `启动.bat`; `http://127.0.0.1:8765` opens by itself after about 3 seconds.

The archive bundles the Python runtime and pip, FFmpeg / ffprobe, yt-dlp, N_m3u8DL-RE and fpcalc, and generates a clean default configuration on first start. **aria2c is not in the package** — the engine of the "磁力 / 种子" (torrents & magnets) page — but you no longer have to hunt it down on GitHub yourself: clicking "install" on the aria2 row under **Settings → Components & dependencies** fetches it into `tools/` (see [Torrents & magnets](#torrents--magnets)).

**From source**

```bash
pip install -r requirements.txt
python server.py
```

The app then serves `http://127.0.0.1:8765`. Changes to `.py` files need a process restart; changes to `static/index.html` only need a page reload.

Linux and macOS use this same route. External tools are matched by the file name *and* by whether that file can actually be executed on the current system, so an apt-installed `ffmpeg` is recognised as present while a `tools/*.exe` carried over from a Windows archive is never picked (and never dies half-way with `Exec format error`). The listening address and port come from environment variables and still default to `127.0.0.1`; configuration, history, cookies, logs and the default download directory can all be relocated at once with `MEDIADOWNLOADER_STATE_DIR`. Without a desktop environment, "open folder" returns a readable explanation instead of a raw `TclError` — the path is meant to be typed into the field.

**Docker (NAS / home server)**

```bash
docker compose up -d --build
```

The image installs FFmpeg, aria2c and fpcalc through apt, so the torrents & magnets page works out of the box —
no separate aria2 service is needed. Configuration, history, subscriptions, cookies, logs and the aria2 session live
in the named volume (mounted at `/data` via `MEDIADOWNLOADER_STATE_DIR`), while finished downloads are bind-mounted
from `./Downloads` on the host. The port is published to the host's `127.0.0.1` only, because the app itself has no
login; change that line in `docker-compose.yml` if you really want LAN access.

Port already busy, a component missing, or you want member-tier audio? Each has a one-line answer in the [FAQ](#faq).


## What is in the portable package

The only real trade-off of the no-install route: the voice stack (faster-whisper plus models, the `audio-separator` / `demucs` separation engines with their torch, the four RoFormer weights, librosa) is gigabytes, so it is not bundled — every red-dot item installs on demand from **Settings → Components & dependencies**, no re-download needed. Separation installs into its **own environment** at `tools/separator/venv` rather than sharing the bundled interpreter; one button on the voice page ("Build separation env") sets it up. aria2c (the engine behind the torrents & magnets page) and psutil (needed to reap the streaming subprocess when a live recording ends) are not bundled either, but both are rows in the **Components & dependencies** table — one button click installs them; aria2c is fetched from its GitHub release into `tools/`, and you only download it yourself when you want a different build. The six front-end framework files (Vue / Element Plus / lucide) **are** bundled, so the first screen asks nothing of any external CDN — offline, a broken proxy or a dead CDN still gets you a mounted page.

- Anything shown as a red dot in **Settings → Components & dependencies** installs on demand with the bundled pip (or with "update all"), so a missing extra never requires re-downloading the package. Restart the launcher afterwards to load it.

- Unpack somewhere that is not `C:\Program Files`, and avoid non-ASCII or spaces in the path (third-party libraries concatenate tool paths).
- Port busy? Create a `改端口启动.bat` containing two lines — `set MEDIADOWNLOADER_PORT=8899` and `启动.bat` — and double-click it. The launcher window now also says who is in the way: before uvicorn starts, the program tries to bind the port itself, and if something holds it, the two cases are told apart — whatever answers `/api/health` is **another instance of this program** (its address is printed and you are pointed at it), and only what does not answer is some other process. Both write one line to the run log and exit with code 1, so the text stays readable in the `.bat` window — previously it was a bare `Errno 10048`, which looked exactly like a hang. A healthy start now prints its "ready" line only after a background thread actually got an answer from `/api/health` (uvicorn's own "running on" line is suppressed at warning level, so a 2.1-second start and a start that will never finish used to show the same four banner lines).

Left unset it equals the program directory, and local behaviour is exactly as before.
- The Git repository holds source, docs and offline self-tests only. No binaries, no downloads: `.gitignore` uses a default-deny allowlist, so new top-level files are ignored until explicitly unignored.

## Features

**Downloading and streaming**

- Paste one link or a batch; it resolves to selectable formats and enqueues, with normalization and de-duplication. Queue-only mode is available.
- Queues support multi-select, pause/resume, pin to top, move to front and "later"; named queues get their own limits, plus a per-host concurrency cap, adaptive 429 throttling and a global speed cap.
- HLS / DASH segments go to the dedicated N_m3u8DL-RE engine (falling back to ffmpeg / yt-dlp); segmented streams can be range-trimmed.
- MKV by default: a single-file mp4 stream is losslessly remuxed, never re-encoded; post-download integrity verification kills "fake success". **A batch that changed container or extracted audio is matched back to the file it actually wrote**, so it no longer reports "0 files written / the file is unusable".
- **A whole collection can land in one folder named after it** (off by default): the layer sits *below* wherever this run would otherwise have written, takes the collection's own title, and never moves what is already on disk.
- Optional embedded cover art, metadata, chapters and per-language subtitles, plus a sidecar `.vtt`; Bilibili videos also save danmaku as `.xml` and embeddable `.ass`.
- Every quality tier in a resolved result carries an estimated file size, and queue cards show the resolution actually downloaded, bytes done / total and the cover image; the speed limit can be split into windows across a day (`00:00-08:00 -> 2M`).
- **After a download finishes, the delivered file is probed again and compared with the tier you picked**: "the file plays" is not the same as "the file is the tier you asked for". A mismatch puts one orange line on the card naming whose fault it is (a higher stream was in the list / upstream never offered that high / the parse list had expired / the height cap did not hold), and the same sentence goes to the run log and `history.json`. Silent when the tier is met, when the pick is `best`, for audio-only and for live recordings.
- Quality tiers are given by height × codec family: when a single 4K exists in both AV1 and VP9 they are two tiers, each on its own stream, and when there is only one codec family the label stays plain "1080p" with no suffix; a chosen audio cap really does go into the format expression. **When upstream returns only risk-controlled low-clear streams, the parse card states on the spot how many streams came back, the highest resolution reached, and why there is no 4K**, and lists the next steps this machine can actually take (cookies, enable PO Token, change egress, update yt-dlp).
- **Live recording can be set to "auto-stop and save after N minutes"**: the global default is in Settings, this session's sits next to "开始录制" (start recording), and each monitored room has its own value; whichever applies decides when it stops, and a stop runs the full save path (reaps the streaming subprocess, finalises the `.part`, clears danmaku and chat files) — the task card shows an "auto-saves in X minutes" countdown.
- **Torrents & magnets** are their own page: download, pick files inside the torrent, seeding supervision, tracker injection, auto-categorisation by name and separate down / up limits — the engine is your local aria2.

**Sniffing**

- The bundled browser extension watches m3u8 / mp4 / ts / m4s requests and pushes the selected ones into the local queue.
- It also receives POST pushes from the third-party cat-catch sniffer and can import the regex rules from its settings export.

**Music**

- Multi-source search (each source has a time budget, and an empty result says why), lyrics / cover / tag writing by title, whole-playlist download, **single-track link parsing** (Spotify / NetEase — QQ says straight when it cannot), source switching, self-built favourites list.
- "Is this the same song?" is one scoring gate: title, artist and duration are scored separately and must clear an acceptance threshold; rejected candidates are logged with the reason.
- Every search row carries a **keyword match score** (0–100) next to its source: how well that row lines up with what you typed, with the title / artist sub-scores and the rejection reason on hover. It does not decide "is this the same recording".
- "Embed cover art" is a real switch: checked, the finished file is read back and confirmed per track; unchecked, the cover the downloader had already put into the tags is **taken back out** too (tags only — no re-encoding — and the same-named image file stays beside it).
- Local library index plus a persistent bottom playback bar; quality requirements reorder results, can refuse to fetch below spec, and finished files are re-verified from their own tags.
- The "lossless reference" adds Qobuz / Tidal **metadata only** (ISRC, duration, bit depth / sample rate, lossless flag) — not a byte of audio.

**Subtitles, AI and voice**

- Per-language subtitle selection, glossary-checked translations, smart line wrapping, bilingual export as SRT / VTT / ASS, hardsub burning.
- After machine translation every line is checked for suspicious output (ten kinds, written to the operation log, with an optional reflective fix pass), and the subtitle's timeline is measured on its own — coverage, largest gap, reading speed — report-only, with an explicit "not computed because the media duration is missing" that is never confused with QC being switched off. The subtitle itself can be edited line by line in the sentence editor: a backup is taken before writing, and the save is refused — naming the moment it was changed — if the file was rewritten by someone else since you read it.
- Four-stage AI pipeline: subtitles → polish → summary → translation, each stage written to disk and re-runnable on its own.
- Local transcription with speaker diarization (click a timestamp to jump), Edge-TTS dubbing, vocal / instrumental separation (two RoFormer weight families and Demucs, running in their own isolated environment, CPU or GPU selectable), stem mixing, muxing audio tracks (several audio files into one multi-track mkv without re-encoding the video), audio analysis (BPM, key, loudness, spectral centroid; a second layer adds beats and song structure), AcoustID fingerprint lookup.

**Automation and operations**

- Telegram: anonymous `t.me/s/` history listing, batch downloads through your own account session, and subscription tracking.
- Four subscription source types (RSS, web-page changes, Telegram channels, music playlists) scanned on a schedule, each with per-subscription rules; before a scan you can get a plan of what it intends to do, and entries the upstream deleted are archived instead of vanishing.
- Three notification channels — Telegram Bot, WeCom, ServerChan — each with separate finished / failed / subscription switches; a send that fails is written to disk and retried on a growing backoff (survives a restart), and a browser desktop notification can be clicked to jump to that task.
- Components and dependencies update from inside the app (one-click batch update, plus an automatic upstream-version check when the app opens), mirror probing, an operation log that records every write action and failure from the UI (**switching pages does not take a line**) and rotates daily, and a one-click redacted diagnostics export.
- **Settings save themselves once you stop typing**, sending only the keys that differ from the snapshot the page opened with (posting the whole blob used to revert changes another entry point had just made); the ten "one rule per line" fields still use the "Save settings" button. There is also a defaults table to read against, so a single item — or every item that differs — can be turned back to its default, with a `config.json.bak-<time>` copy kept first whenever secrets or machine-specific paths are involved.
- The whole HTTP surface is additionally exposed as an MCP bridge (`mcp_server.py`, loopback only) so MCP-capable agents can call the app directly.
- 5 accent themes × light / dark; **the interface is bilingual** (an `AUTO / 中 / EN` group in the header, following the browser by default, with all 17 page bodies in the dictionary); the sidebar collapses to icons only, `Ctrl+K` jumps to a page, a sticky banner sits at the top, and rows have a right-click menu; every bit of data stays local.
- **The first screen asks nothing of any external CDN**: the six framework files ship in `static/vendor/`, so offline, a dead proxy or an unreachable CDN still mounts the interface.

<details>
<summary>Navigation: collapsing the sidebar to icons, what the `Ctrl+K` panel does and does not do, what the sticky banner carries, why the right-click menu keeps no action list of its own</summary>

- **The sidebar collapses to icons only** — one button at the right end of the title row takes 212 px down to 64 px: group headings go, a hairline replaces them between groups, each entry is identified by its hover title, and badges move to the corner of the cell (a 47 px cell cannot hold them where they were). Collapsing is stored in the browser only — the same convention as read-only view preferences — never in configuration, never on the backend, and it changes nothing but the 148 px handed back to the main area. In the collapsed state the button wraps under the icon instead of both being squeezed: that would leave about a dozen pixels, which is to say nothing you can hit.
- **`Ctrl+K` jumps to pages and runs actions that are already on screen — it does not search content.** Resources / favourites / history / queue each have their own filter field; a cross-page content search would have to pull five lists into the header, then switch page and locate the row, which is a different piece of work, and that boundary is stated in the header hint itself. The panel lists the 17 pages plus five actions (back to the download page with the link field focused, collapse / expand the sidebar, switch light / dark, switch interface language, pause or resume the whole queue); after collapsing, that row relabels itself as "expand the sidebar". Matching reads three sources: page names in the current language, page names in the other language, and an alias table used only for matching and never displayed. The query splits on spaces and every word must hit, so "aria2 queue" leaves exactly one row. Arrow keys move the selection, wrap at both ends, Enter runs it.
- **The sticky top banner carries only what is true right now but visible only inside some page**: components have new versions, notifications are owed and unsent, a domain was throttled and slowed down. Those three used to hide in Settings → Components, Settings → notification outbox and the turtle card on the queue page, so while you were on the download page you never saw them. One row per cause; anything actionable is acted on inline (go update / resend now · see queue / lift the throttle) and what cannot be is announced without doing it for you. Dismissing is remembered per cause id for the browser session, so one cause is dismissed once, and switching pages or scrolling keeps the rest. The automatic update check's popup became a banner row; **the manual "check now" popup stayed** — a click you asked for deserves a receipt, not another strip.
- **The right-click menu keeps no action list of its own.** Right-clicking a table row / task card / native row lists the buttons that row actually has, and choosing one is the same as clicking it — the action's own logging, confirmation and success / failure feedback still run, so there is no second source of truth that can say something the template no longer does. **Yielding is part of the spec too**: right-clicking an input, a select or a checkbox, right-clicking while text is being selected, or right-clicking a row with no actions at all takes over nothing, and the browser's own menu (paste, copy selection) stays available. The destructive item is coloured from the button's own danger class, **not by guessing from the word "delete"** — once the dictionary switches to English, a literal-word heuristic silently stops working.
- Two smaller cleanups: the 16 items in the files page's inline "more" menu are divided by family (transcribe / pipeline / vocal separation / subtitle tools / music tags), and the Picard family is the first item of the whole menu for `flac` / `ogg` / `wma` / `opus`, where the divider has to disappear; the file browser sorts by modification time descending by default, matching the resource library — the backend was not touched, because this page's sorting is entirely front-end and changing the other side would do the same job twice. The "hint text sits half a line below the control beside it" class was measured first (31 rows across 17 pages) and every one had the same cause: a 6 px top margin on the hint, since flex centres the margin box, not the content. Standalone hint lines kept their spacing.

</details>

<details>
<summary>List behaviour: pagination rules, what header sorting covers, aggregate-search ordering and result caps, which single-line fields support right-click paste, where the two primary buttons sit</summary>

Lists longer than one screen (queue / files / history / aggregate search / music / Telegram / favourites / subscriptions / resources / web sniffing / live) paginate at 50 rows with previous, next and jump-to-page; the pager is hidden when there are fewer than 50 rows. Header sorting applies to the whole result set, not just the current page. Favourites / following fetch all upstream pages (Bilibili collections 500, following lists 2000, YouTube playlists up to 200); when a real cap is hit the table says so above it.

Aggregate search can sort by relevance, view count or publish date. Changing the sort re-fetches with the platform's own sort parameter (Bilibili `order`, YouTube `sp`) rather than re-ordering whatever the front end already holds. One platform, one content type returns 100 items per request; the aggregate result caps at 300, and the results area states how many the upstream returned when it was cut.

**Right-click "Paste" and `Ctrl+V` run the same cleaning as the "Paste" button.** Seven single-line fields carry a paste handler (`@paste="onPaste($event, …)"`): the media-link field on the media-info page, the playlist link on the music page, the channel name on the Telegram page, the live-room URL on the live page, the YouTube playlist field on the favourites page, the keyword box in aggregate search, and the auto-categorisation test field on the torrents page. URL fields take the first link through `extractUrls()` and drop trailing punctuation and wrapping quotes, so pasting a whole share message leaves only the link; keyword and test fields keep the first line and collapse runs of spaces. The result is identical to pressing "Paste", and those buttons stay where they were. Multi-line list boxes (home-page media links, magnet input, subscription addresses, live monitor list) are deliberately left unbound: the pasted text stays verbatim so you can read it back, and normalisation happens when it is parsed.

**Clipboard watch (off by default).** When `clipboard_watch` is on, the **local service** reads the system clipboard text every 2 seconds; when it recognizes a `magnet:` or `http(s)://` link, the home page shows a "1 link found in the clipboard" card with exactly two buttons: **加入 (Use)** and **忽略 (Ignore)**. "Use" only puts that link into the home-page input box — whether it gets parsed or downloaded stays behind the button you press; the program never enqueues or starts a download by itself, and the card is still there when you come back with the page closed (the watcher is a process, not a page). This is deliberately not the browser's `navigator.clipboard`: that one only works while the page is open and is frequently refused over non-HTTPS, whereas here a local process reads a local clipboard. The limits are written into the implementation: text format only (images and file lists are skipped and are not treated as an error), no link extraction from blobs longer than 4000 characters, the same content asked only once (fingerprints of the last 30 clipboard contents, in memory, so copying an old entry back does not pop again), and once the switch is off the thread never touches the clipboard again. **What it reads is never written to the run log or to any state file** — `GET /api/clipboard` hands only the extracted link to the local browser over loopback. Switching the feature on or off logs one line each (who let the program start watching the clipboard, and when, should be auditable; what it saw should not be kept on disk).

**The two primary buttons sit at the end of the input row.** The "确定解析" (confirm parse) button on the media-info page and the "开始搜索" (start search) button on the aggregated-search page share one flex row with the input (the field is `flex:1; min-width:240px`), so once you finish typing you press Enter or click the rightmost button instead of looking one row lower; "paste" and "clear" stay on the row below.

</details>

<details>
<summary>Settings: how edits get saved on their own, which keys are sent, the ten multi-line fields that still need "Save settings", and what per-item / one-click restore-to-default restores</summary>

**Auto-save sends the changed keys, not the whole blob.** When the settings page opens, the front end keeps a snapshot; 700 ms after typing settles, only the keys that differ from that snapshot are sent to `POST /api/config`, and the snapshot of those keys is refreshed from what the backend returns. Previously pressing "Save settings" posted the entire settings object, so anything another entry point had changed after you opened the page — another browser tab, or the program writing a key itself — was overwritten by your stale copy. Nobody did anything wrong; a setting just reverted.

**Edits made during a write are not lost**: if new changes arrive while one write is still in flight, the next round is re-queued as soon as that write lands, instead of this round being dropped. **Keys the backend does not know, and `null` values, are named instead of pretending to be saved**: before sending, candidates are filtered against the key names `GET /api/config` actually returns, so an unknown key is reported as "the backend has no such key", and a `null` / `undefined` value is reported as "this one was not sent" — a null means "leave this key alone" at the backend, so sending it would have changed nothing anyway. **Ten fields still save manually**: speed windows, the queue run window, per-queue windows, custom yt-dlp arguments, magnet auto-categorisation rules, the tracker list, tracker sources, per-platform proxies, the access-protection master switch and the subtitle glossary — all of them multi-line "one per line" boxes, where saving mid-typing would store half a line as a rule.

**Restore-to-default is a table you can read** (`GET /api/config/defaults`): each row gives the Chinese label, a summary of the default, how the current value differs and a "restore this item" button; the "restore all" button in the header only covers the rows marked as differing, and both go through the same `POST /api/config/reset`. **Of the 200 keys in the default table, only 163 can be written from the UI, and those 163 are exactly what the table offers** — the other 37 have no configuration write path (they are dropped when the request body is built), so listing them would produce the "clicked restore, nothing happened" experience. A request for keys that are all outside the list is refused with 400 naming each one; a mixed request restores what it can and returns the untouched keys in `refused`, which is also what the log says. Whenever a single call restores more than one key, or touches a secret or a machine-specific path (download directory, cookie file and cookie source, ffmpeg / aria2 paths, per-platform cookies), the current file is copied to `config.json.bak-<time>` first and the UI states where it went — the naming follows the subtitle editor's backups (an extra counter within the same second), the file is reaped by the "edit backups" group of age-based cleanup, and it never ships in a release package.

**Four keys are not in that table, and "restore all" cannot reach them either**: `secret_key`, the access-protection password hash, the machine token and the CookieCloud sync key — they are the lock and its keys, not settings. **A machine token cannot open this door**: `POST /api/config/reset` answers 403 to a machine token that is not accompanied by a session — the same rule that refuses machine tokens on config writes carrying `web_auth_*` keys — so restoring defaults has to come from a logged-in UI session. **Clicking restore first flushes whatever edit is still inside the 700 ms wait**, otherwise the value you just typed would be reverted while the snapshot still believed it had been saved. Self-test: `tests/settingsave_test.py` (111 checks, writing only to a fake `config.json` in a temporary directory, and finishing by proving the real file was never touched).

</details>

<details>
<summary>Operation log: what kinds of events get in, what does not, and why "switched to page X" was removed</summary>

**What gets in**: every write action from the UI (saving settings, starting a download, deleting a task, clearing history, installing a component, syncing cookies…) and its failures — a failure is logged as a warning with "（失败）" appended, and the error is still thrown to the caller, so telemetry never swallows it. These all go out through the one tracked branch in `api()` to `POST /api/ui_event`; `uiName` distinguishes the case where several buttons share one endpoint, each line is capped at roughly 200 characters, and sensitive wording (passwords, tokens, keys) is replaced with `[已隐藏敏感参数]` before it leaves the browser.

**What does not**: ① GET reads, including progress polling — one line per tick would leave nothing but noise; ② the handful of calls that explicitly pass `noLog`, typically the NetEase QR-login status poll (asked every few seconds; logging each ask would bury everything else); ③ **switching sidebar pages** — each click used to add a "切换到「X」" line, and since the log page shows only the most recent 200 entries, walking through the 17 pages consumed 17 of them while contributing nothing to troubleshooting (such a switch writes nothing and fetches nothing). **Where the line was drawn**: one-off jumps caused by something outside the app are still recorded (clicking a desktop notification to reach the queue or torrents page, clicking the update popup to reach components), because they say how the user got there and happen once, not repeatedly; theme and light/dark toggles are still recorded, since they really do write `ui_theme` / `dark_mode` into `config.json`.

The backend endpoint does not judge what arrives: it only flattens whitespace, truncates at 200 characters, accepts `level` as info or warning (**this path cannot produce an error-level line**), skips blank text, and does not de-duplicate — sending the same sentence twice records it twice, because de-duplicating would erase "the user really clicked twice". Self-test: `tests/navlog_test.py` (43 checks; the `watch(page, …)` callback body and `api()` are lifted verbatim into the local node — flipping through all 17 pages emits zero events while the twelve pages that must load data still do, and putting the old line back turns three assertions red).

</details>

## Download & queue

Paste → resolve to selectable formats → enqueue. If something this job must have is missing locally, pressing “start download” fails on the spot, names the exact row to install from, and creates no task at all.

<details>
<summary>Details: the pre-enqueue dependency check, named queues, per-host concurrency and where 429 throttling is triggered, speed limits (global / time window / per task), queue run windows, MKV remux and integrity verification, whole collections landing in one folder named after them, matching a container-changed batch back to the file it wrote, why range trimming only works on segmented streams, how the quality tiers are ordered, per-tier size estimates, playlist range selection, the gate on custom yt-dlp arguments, output filename sanitising, live auto-stop after a set duration and the per-room settings, age-based cleanup and how it holds the "look at the list first" line</summary>

- Multiple URLs can be pasted at once; they are normalized and de-duplicated. "Queue only, download later" enqueues without starting. This box, like the magnet input, the subscription addresses and the live monitor list, is multi-line: pasted text is kept verbatim and normalized only when parsed — the right-click paste cleaning described in [The 17 pages](#the-17-pages) applies to single-line fields.
- **Dependency preflight before enqueueing**: if you press "start download" and this machine lacks something the job must use — yt-dlp for site resolution, FFmpeg for subtitle / cover / chapter embedding, MKV muxing or range trimming, faster-whisper for local transcription, N_m3u8DL-RE for HLS, telethon for `tgmt://`, or a download directory you cannot write to — the request fails on the spot, naming which row of **Settings → Components & dependencies** to install, and **no task is created at all**. The refusal is also written to the operation log. Cases that merely make things slower or lower-quality (no FFmpeg but a direct mp4 download) are not blocked; they get a log note.
- Queue: multi-select, pause / resume, pin to top, move to front, download later; task cards show "pinned" and "later" badges, plus the resolution this task actually downloaded, bytes done / total and the cover image (`1080p HDR 60fps · 420.0 MB / 1000.0 MB`, with the full sentence on hover). Those fields ride on the SSE progress frame, and a field that was never measured is simply left out — the card never shows a placeholder "0 MB".
- **Named queues** `queue_name`: `default` / `night` / `subscribe` / `sniff` (configurable via `named_queues`; batch music uses `music`). Speed limits and gating can be set per queue.
- **Link-based destination for ordinary downloads**: the same rule table as torrents, using the rules whose `scope` is `url`. Before a task really starts, the download loop asks which link rule this URL hits (`url_target_dir`) and, on a hit, moves that task into the rule's subdirectory under the download directory, logs "…contains 「youtube.com」 → rule 「网页视频」, this one goes to …" and tags the task card with the rule name. Three boundaries are settled in advance: **① a directory you picked yourself wins** — that field is pre-filled with the global directory, so only a genuinely different path counts as manual (compared after normalization, so case and a trailing slash are not a difference); in that case the rule leaves the destination alone but still logs the hit, because otherwise you would assume the rule was broken. **② name rules never participate** — a plain URL has no torrent name, so only `scope=url` is asked. **③ no `bt_auto_fallback`** — that slot exists for magnets whose name is not known yet, and applying it here would relocate the whole download directory on the strength of one link rule, so a miss stays in the default directory. With no `url` rule configured at all this code never asks, so an upgraded install behaves exactly as before (no "extra directory appeared while I left the defaults alone").
- **Whole collections can land in one folder named after them** `playlist_subdir` (off by default): only when it is ticked does an extra layer appear, named from the collection's own title (Windows-illegal characters replaced, reserved names given a leading underscore, cut at 60 characters, **never numbered**); when nothing usable is left after cleaning the title, no folder is created and the log says plainly "this batch still lands flat in …". **The layer is added *below* wherever this run would otherwise have written** — the download directory, or the subdirectory the auto-classification rule above matched; it does not replace it. The name has two sources: the "download the whole table" button takes the container title that resolution itself returned, while "download all / selected episodes / re-download one" run as N independent tasks with no container in hand, so they take the playlist name the parse page hands over at the moment of enqueueing (cleared once handed over, so a previous batch's name cannot leak into the next). Neither source found means flat — no fall-back to a folder name nobody would guess. The layer is `mkdir`ed at the moment the queue is built: the "whole collection saved to X" log line must be able to point at something that really exists, not report first and create later. When it cannot be created (a file sits on that path, permissions) the run falls back to the original directory and says why. Single downloads and live recordings stay flat (a recording is a stream, not a collection); **files already on disk are never moved** — renaming or unchecking only affects what you download afterwards. **Why the filename template cannot do this**: that field replaces `/` and `\` with underscores before rendering (the `Path(out_dir) / template` step in `server.py`), so no template can ever open a subdirectory; the earlier example `%(uploader)s/%(title)s` was made up and the documentation now says so. The judgement lives in one place (`playlist_landing_dir()` / `playlist_folder_name()`), covered by `tests/playlistdir_test.py`.
- **Per-host concurrency cap** `max_per_host` (default 2) combined with **adaptive 429 throttling** `adaptive_throttle`: after a site rate-limits you, that domain is temporarily dropped to one concurrent connection and put into cooldown (duration taken from "risk control → 429 cooldown (seconds)", which is also the value used for anti-bot challenge-page classification). A "site throttled" bar appears at the top of the queue page and can be reset immediately. Triggers are not limited to HTTP 429 inside the download loop: a Douyin search classified by `risk_control` as "rate limited" or "anti-bot challenge page" marks the same throttle point, as does a download failure in either category. A "login required" verdict deliberately does **not** mark the point, because slowing down does not help. The Douyin search entry checks this table **before** sending anything: while still in cooldown it repeats the previous verdict on screen (`本次没有再向它发请求`), sends zero requests and does not add another strike — otherwise every extra click would extend the penalty on the same domain, and retrying is the only action available to the user. To really search before the cooldown expires, click "resume now" on the throttled bar.
- **Global speed limit** `global_speed_limit` (e.g. `2M`) — either this or the per-task `speed_limit`.
- **"Skip already downloaded" keeps one record per kind of output**: each line of yt-dlp's `download_archive.txt` is only
  "site key + video id" with no format, so asking for audio-only after the video had been downloaded counted as done and
  nothing was fetched (the queue row still pointed at the old mkv, which reads as "I asked for audio and got a video").
  Audio-only now records into `download_archive_audio.txt`; the video file keeps its exact name so nobody's existing
  records are invalidated, and presence asks "has **this kind of output** been downloaded" - video first then audio-only
  really downloads, while a second click in the same kind still skips. "Clear download records" clears both.
- MKV by default: when the site offers a single mp4 stream the file is only losslessly remuxed, never re-encoded. Downloaded files are verified for integrity to prevent "fake success"; failure reasons are translated into plain language with the original error attached.
- **A batch that changed container is matched back to the file it actually wrote** (`resolve_written_file()`): with a target container of mkv / mp4 / webm (`FFmpegVideoRemuxer` attached) or audio extraction, yt-dlp finishes and writes back the *pre-remux* path in each episode's `filepath` (`.webm` / `.mp4`) while the finished file lies beside it under a different suffix. Trusting only that name, the episodes branch tests each path for existence and therefore marks the entire batch missing — first "the list had N items, this run wrote 0 files into the download directory", then an empty `filepath` renders a name ending in `.NA`, and integrity verification closes it out as "download completed but the file is unusable" — while the `.mkv` was on disk all along. The single-download branch already had a "same base name, another extension" recovery loop; the episodes branch did not, which is why only batches were hit. Now a reported name that exists is used as-is, and only when it genuinely does not exist does the code look for the same base name under another extension, **trying the container this run asked for first** (an older `.mp4` left by a previous choice can sit right beside this run's `.mkv`, so the target container has to be ranked ahead or the wrong file gets claimed). If no candidate exists the original name is returned and "file does not exist" is said as it is — this layer never covers for the tool. The finished-container list `REMUX_FALLBACK_EXTS` is defined once and shared by both branches. The two "hit a download record" wordings are untouched; that is a different kind of "no file". **This round fixed the shape, not the record**: the "download completed but the file is unusable" lines and `.NA` titles already written to history are not rewritten — searching the download directory for the same base name under another extension finds those finished files, all of them. Covered by `tests/remuxcount_test.py`.
- **The delivered resolution is read back and checked against the requested tier** (`tier_readback()`): integrity verification only proves the file plays, not that it is the tier that was clicked, which is exactly how a silent 4K → 1080p download used to end up reported as success. The finished file is probed with ffprobe and, when the height does not match, the card shows one orange line — the same sentence lands in the run log and in `history.json` (visible as the tooltip on the status tag, since the history table got no extra column). **Four causes are worded separately rather than collapsed into "did not reach 4K"**: the list contained a higher stream → the loss happened in selection/merging here; the list tops out at what was delivered → upstream simply does not offer that tier; the parse list expired → only the delivered height is stated, and the note says it cannot tell whose fault it is; delivered clearly above the cap → the height cap did not hold (custom arguments, or a site with a single stream). Nothing is said when the tier matches, when the pick is `best`, for audio-only tasks, for live recordings (their format is always `best`, so a tier verdict would blame the wrong layer) and for the few rows that codec alignment adds on top (2176 / 1088) — otherwise the line would fire on almost every download and stop being read. The height table (`VIDEO_QUALITY_HEIGHTS`) is now defined once and feeds the format expression, the per-tier size estimates and this check, because a hand-copied second copy of it is how the three drifted apart.
- **Expected checksum verification** (`expect_hash` / `hash_algo`, `hash_readback()`): the fine-controls block gained an optional field for the digest a publisher ships with the file (MD5 / SHA-1 / SHA-256 / SHA-512). After a successful download the finished file is hashed with the same algorithm and compared. **The length identifies the algorithm** (32 / 40 / 64 / 128 hex chars); a pasted `md5:` / `SHA-256=` prefix, stray spaces and UUID-style hyphens are normalized away first. Naming the algorithm explicitly exists to catch "one character got lost in the paste" **at enqueue time** — that is the only moment in the whole chain where it is still actionable; after the download the same mistake yields a useless "does not match". Base64 is rejected by name (hex only), and an ambiguous `sha` / `sha2` is left to the length, erroring out when even that cannot decide. A match adds nothing to the card (an orange line every time would stop being read); it leaves one log line ("checksum verified: MD5 matches (…)") and a note in the card title's tooltip ("checksum ok · MD5 754a369d0817…"). A mismatch is the whole difficulty of this feature and is therefore worded two ways: link downloads normally still remux the container and embed cover / metadata / chapters / subtitles and cut SponsorBlock segments, each of which rewrites the file bytes, so hashing the finished product against a publisher's digest of the *original* is expected to fail — that sentence names exactly which steps rewrote it (`hash_rewrite_steps()`) and says the check only means something for torrents/magnets or a file that landed byte-for-byte. Only when the file demonstrably landed as-is (magnets and torrents, or the CDN-direct branch — the engine records that fact per `task_id` and hands it to the finisher instead of letting it guess) does the card say "this is not the file that was expected (wrong upstream digest, a truncated download, a mistyped algorithm); the file has been kept, nothing was deleted". A file that cannot be read says only "cannot tell". aria2's own `checksum` option was deliberately **not** used: its semantics are "delete on mismatch", and one digest cannot cover the several files a torrent produces. The comparison lives outside the `verify_download` gate — integrity says "the file plays", the digest says "it is this file", and a torrent only wants the second sentence — runs only for successful tasks, and a failure inside the check itself is logged and skipped rather than turning a finished download red. **Only that `verify_note` sentence reaches `history.json`**; `hash_state` / `file_hash` are not persisted, so after a restart the mismatch line is still visible while the positive "matches" confirmation lives only in the run log.
- **Extras** checkboxes: embed cover thumbnail (`thumb`), metadata (`embed_metadata`), chapters (`embed_chapters`). Bilibili videos additionally save danmaku as `.xml` plus an embeddable `.ass`.
- **Range selection** `download_section`: enter `00:01:00-00:02:30`. Under the hood this uses yt-dlp's `download_ranges` with a forced `*` auto-segment prefix, **so only HLS/m3u8-style segmented streams can be trimmed**; for single-file streams the parameter is ignored and the task log says so.
- **Quality tiers are ordered by "height × codec family"** (`_quality_presets()`): when one 4K exists in both AV1 and VP9 they become two tiers (`2160p · AV1` / `2160p · VP9`), each taking its own stream; when there is only one codec family the label stays plain `1080p` with no useless suffix. Picking a tier uses that stream's own `format_id`, and the video+audio expression carries the audio cap chosen in the UI (`abr<=N`). A source with only progressive streams (audio and video in one) **has no separate audio track**, so the whole row of audio-quality chips is hidden and replaced with a note that "audio follows the resolution — there is nothing to choose"; passing off a progressive stream's combined audio+video bitrate as an audio tier would change nothing when selected.
- **When upstream returns only risk-controlled low-clear streams, it says so plainly** (`_format_gate_note()`): the parse card states "only N streams came back this time, the highest is 1080p, and they are all progressive — the site is applying risk control to this egress", then lists the actionable next steps for this machine (cookies / enable PO Token / change egress + update yt-dlp) with a "去设置" (go to settings) button that jumps straight there. The PO Token step is worded per **switch / service / plugin** (`_po_gate_tip()`): if the switch is off it says the switch is off; if the switch is on but nobody answers `127.0.0.1:4416`, it names the address you configured, reports what the probe said, and explains that the token-minting service lives in `tools/bgutil-pot-server/` and the program starts it with the local `node` as soon as the probe finds the port empty — it only stays down when there is no `node` on PATH; it mentions the yt-dlp plugin only when that plugin is missing. **It never tells you to enable a switch that is already on.** And this wording only appears after the program has actually tried: when a list contains no video-only track at all and a `player_client=all` attempt is still queued, parsing does not stop there — it re-resolves with `all` and keeps the better list (`_yt_widen_attempt()` / `_yt_has_dash()`), because high resolution needs **both** a minted token *and* a client that spends it. Only when the token layer is fine *and* `all` has been tried does `_po_ready_tip()` say "the PO Token layer is fine (plugin installed, `<the address you configured>` is minting tokens), the `all` client was tried too, and there is still nothing higher in the list — this time it really stops here", which is where changing the egress becomes the remaining lever. Tiers upstream never sends cannot be conjured up in this program; what it can do is not leave the user thinking they simply failed to tick the right box.
- **Estimated size per quality tier**: every tier in the resolved result carries a size estimate derived from that stream's bitrate times duration (`_estimate_tier_sizes()`; the audio-only tier does not double-count the video track). When no stream exists above the requested ceiling, it **falls back to the highest stream actually available**, and the fallback never produces a value larger than `best`; when the video cannot be looked up at all it is not reported as "computed, size 0".
- **Playlist / collection range picking**: two index boxes (from / to) show live "range start: item N 《title》", "tick this range" checks them in bulk, and nothing is submitted until you press download. Index ranges and per-row ticks coexist (tick 5–9 where one item was already downloaded and the message reads "added 4 tasks").
- **Custom yt-dlp arguments** `ytdlp_extra_args`: one field in Settings applies globally, one field on the home page applies to that batch (task level overrides global). **This is not a verbatim pass-through** — each item goes through a gate, and anything refused is named one by one with a pointer to where it belongs: `--exec` (runs an arbitrary command after the download), `-f` / `--format` (the format comes from the tier picked on the home page; to pin a specific stream use "format id"), your own cookies (that belongs on the Settings page), external config files, arguments that change failure handling, and presets that implicitly select a format. Accepted arguments are not held hostage by refused ones; the dialog that says "saved, but N arguments did not take effect: …" stays open so you can fix them and save again.
- **Speed limits by time window** `speed_windows`: one entry per line, `00:00-08:00 -> 2M`; `->` `=>` `→` a bare space `=` `–` `~` and the words "至" / "到" are all accepted, full-width colons are normalised, up to 30 lines. Precedence is **per task > matching window > global**; the "check it" button on the card (`POST /api/config/speed_windows/check`) judges the settings alone and never touches the per-task override, reporting how many windows were parsed, which lines are malformed, and which window the current clock hour falls in.
- **Only start new tasks inside a time window** `run_window` / `queue_windows`: one global field in Settings (one entry per line, `22:00-06:00`; a start later than the end is read as crossing midnight, `#` or `//` starts a comment, and a line copied over from the speed-window field such as `09:00-12:00 -> 2M` just keeps its first half instead of erroring), plus an optional window of its own per named queue (`{"night": "22:00-06:00"}` — a queue that has one is governed by it alone, not by the global layer). **It only decides whether new tasks start; anything already downloading is never interrupted.** When the window opens, a timer armed with the real remaining time pumps the queue again (the cooldown path that caps at 900 seconds is useless here — opening can be six hours away). Leaving it blank means always open, so an upgraded user who never touched this field behaves exactly as before. The card's "check format" button (`POST /api/config/run_window/check`) names every line it cannot parse and says whether the gate is open right now and when it will open; `09:00-09:00` (neither a full circle nor zero), `24:00`, and a queue name that does not exist are refused with 400 at save time, and saving pumps the queue immediately rather than waiting for the next event. The queue page gained a banner for this (fed by the new `window` field on `GET /api/tasks` and the SSE `state` frame) listing, per queue, "N waiting · auto-resumes at HH:MM". The SSE structural signature only tracks open / resume time / how many are held — the countdown to the next opening is left to the UI, so a ticking minute never re-sends the whole task table.
- **One output filename sanitiser**: `safe_filename_component()` is the single entry point for Windows-reserved characters and reserved names, plus zero-width and directional control characters (`\u200b-\u200f`, `\u202a-\u202e`). **Multi-suffix names are not truncated** (`app.tar.gz` stays `app.tar.gz`), and **reserved names are checked only after truncation** (truncating can itself produce `CON` / `NUL`, in which case an underscore prefix is added). The Telegram batch path uses the same routine — there is no second regex any more — and when sanitising changed the name the log says so.
- **Per-room live recording settings**: each monitored room gets six own settings — container (follow the app setting / mkv / mp4 / webm), quality tier, transcode preset (e.g. "转 MP4（重编码 + AAC，编码器见设置）", "转 MP4 并限制 1080p", "抽取音频 MP3"), maximum recording length (`0–1440` minutes, 0 = follow the default in Settings), and a monitoring window start / end (crossing midnight works, e.g. 20:00–02:00; filling in only one end has no effect). All six are stored in `live_monitors.json`; illegal values are refused item by item and never persisted. Reaching the room's own length cap ends that recording on its own and pauses the room (it resumes after the stream goes off air), logging "本房间已录满 N 分钟，自动结束录制"; outside the window the room still reports "直播中(不在监控时段 …)" but starts no task at all.
- **"Auto-stop and save after N minutes" now covers the manually started recording too**: previously `最长录制时长` (maximum recording length) only governed the sessions a monitored room started automatically — a recording you started by hand had no room setting to hang on and ran until someone ended it manually. Worse, the finish check `_live_recording_tick()` used to sit inside `if items:`, so a user who never added a monitor never ran it at all. Now the three inputs share one decision, `_live_effective_minutes()`: **the non-zero value entered for this session > the room's own non-zero value > the "直播默认最长录制（分钟）" (default maximum live recording, in minutes) in Settings > unlimited**, always clamped to 0–1440. The check was moved out of `if items:` and runs every tick (`_live_used_seconds()` counts a queued task with no `started_at` as 0 seconds, so it is not killed the moment it arrives); the end action carries a reason (`end_live_tasks(ids, reason=…)`), so the task card now reads "已录满 N 分钟，自动结束并保存" instead of the previously hard-coded "user ended recording". An automatic stop runs the full save path (stop the streaming subprocess → finalise the `.part` → clear danmaku / chat files), `to_dict()` returns `live_limit_min` for live tasks, and the UI shows an "auto-saves in X minutes" countdown.
- **Age-based cleanup** (`GET /api/cleanup` reads this layer; `POST /api/cleanup/account` / `/preview` / `/run` / `/restore` plus `GET /api/cleanup/trash` are the five actions, all on one "cleanup by age" card in Settings): **off by default**, four day-thresholds each governing one group — log archives `app-YYYY-MM-DD.log` (`cleanup_log_days`, default 7; the startup log rotation reads that same value), edit backups `.bak-<time>` (`cleanup_backup_days`, default 0), finished downloads (`cleanup_download_days`, default 0), and whatever has ripened inside the trash folder (`cleanup_trash_days`, default 30). **Age is measured by file `mtime`** (when the file was last touched), not by the timestamp in the history record; 0 means "this whole group is not scanned", so anyone who never filled these in behaves exactly as before. **Finished files are never hard-deleted**: downloads and backups first move into `<download dir>/_cleanup_trash/` (relative paths preserved, a `manifest.json` beside them records where each one came from) and are only really deleted by the "trash ripened" group once they have sat there for `cleanup_trash_days`; log archives are deleted outright. Anything in the trash can be put **back where it came from** at any time — and if the original slot already holds a file of that name **it is not overwritten** (that one may be a fresh re-download); the blocked entry stays in the manifest for another try. **The automatic pass never touches finished downloads** — `CL_AUTO_GROUPS` is logs / backups / trash, and that is a code-level fact, not a matter of which buttons the UI shows. One `threading.Timer` alarm schedules it daily at `03:05`; if the process started after that hour, the missed pass is caught up at boot, at most once per day. A manual delete goes through **two dry runs**: "show the list" only computes the list, sizes and a fingerprint without touching a byte, and "delete per list" must carry that fresh fingerprint — the backend compares it (409 "the disk changed in between" when it does not match), checks the ten-minute TTL, then **recomputes the list and compares once more** before moving anything. The client only ever sends group names; paths are always recomputed server-side. Files belonging to queued, downloading, paused, later **and still-seeding** tasks are protected (a seeding task protects its whole directory: files in a seed folder can be very old by `mtime` and look deletable while being in use) — they never appear in the list, they are checked again at run time, and both the log and the UI report how many were protected. The trash folder and its subdirectories are skipped by the media library, files moved out are dropped from `library_cache.json` (they come back on the next scan), and symlinks are never followed for deletion — that would delete content outside the drive. `.part` / `.ytdl` files remain the job of the existing "clean temporary files" button; the two do not overlap. The switch and the four thresholds **can only be written through `/api/cleanup/account`**, and a machine token hitting that endpoint gets a plain 403 — "a token that can write settings" should not be able to flip the switch that deletes files. `cleanup_state.json` records only when the last pass ran, which groups, how many files and how much space, and sits on the packaging exclusion list next to `config.json`, `notify_outbox.json` and `login_state.json`. Self-test: `tests/cleanup_test.py`, 159 checks, writing only into a temporary directory (including the edges "an empty trash reports 0 files, not 1", "a lone manifest is not a finished file", "0 days skips the whole group"; the last three in section A guard the packaging itself — no file meant to ship may be matched away by `pack_release.py`'s exclusion regex (a stray `|` there is an empty alternative that matches every filename and turns the bundled UI into an empty shell), the private files stay matched, and a pre-build gate aborts the zip when a required file or directory is missing).

</details>

## Torrents & magnets

Magnet links and local `.torrent` files live on the sidebar's torrents page (磁力 / 种子), where downloading, seeding, tracker injection, categorisation and speed limits are handled together. **This page runs entirely on aria2**: with no usable aria2c on the machine, pressing "start download" says on the spot what is missing (and names which row of "Components & dependencies" to install) and creates no task at all.

<details>
<summary>Details: the aria2 RPC and auto-start, how a missing aria2c is installed and what its errors say, trackers fetched at runtime and cached, the injection cap, seeding supervision, auto-categorisation and rule testing, what only applies to new tasks, seed-only mode</summary>

Five sections on the page: **add magnets or torrents** / **torrent tasks** / **trackers & speed limits** / **auto-categorisation** / **aria2 & seeding**.

- **Handed to aria2**: `aria2_client.py` speaks JSON-RPC (`aria2_rpc`, empty means `http://127.0.0.1:6800/jsonrpc`, optional `aria2_secret`). When nothing answers the RPC, `aria2_autostart` (on by default) makes the program launch its own aria2c **listening on 127.0.0.1 only** (`aria2_daemon.py`, shut down when the app exits); with `aria2_bin` empty it tries, in order: the path set in Settings, `tools/`, the `MEDIA_ARIA2_BIN` environment variable, then PATH — and it only accepts a binary the current platform can actually exec (a Linux container will not pick up a bundled `aria2c.exe`). The "check aria2" button now actually starts the process rather than only reading state — its response carries `ensure:{ok,why}`, shown on the status line — and `GET /api/aria2/status` re-reads `daemon` ownership (whether this program started it, its PID, whether it is alive) after a successful auto-start, so the UI cannot say "not ours" moments after we launched it. With no aria2c on the machine at all the row no longer just self-reports "未安装" (not installed): it lives in the Components & dependencies table, where "install / update aria2c" (`POST /api/update/aria2`, through the GitHub mirror prefix in Settings, switching sources automatically on failure) fetches `tools/aria2c.exe` and starts it right away.
- **aria2's errors are turned into plain language**: `aria2_err_cn()` (server.py:4171) takes raw text like `<urlopen error [WinError 10061]…>` ("the target machine actively refused it") and rewrites it, per platform, into a next step — a missing executable points at "click install on the aria2 row under Components & dependencies" or "press "check aria2", it auto-starts one", while connection timeouts and the key-bearing 401/403 each get their own branch. Before the seeding panel reads aria2's active tasks it first checks whether the RPC answers; if not it calls `bt_ensure()` to try a launch and writes the reason into that line, instead of reporting "读 aria2 活动任务失败" (could not read aria2's active tasks) every 30 seconds.
- **Adding**: one `magnet:?xt=urn:btih:...` per line; a local torrent as `file:///H:/…/影片.torrent` or a plain drive-letter path, or pick "upload torrent" to choose a `.torrent` (`POST /api/torrent/upload`). Lines that cannot be recognised are not counted and the message states how many were ignored; a magnet missing `xt=urn:btih`, or with a hash that is neither 40 hex characters nor 32 base32 characters, fails naming which line.
- **Seed only**: when the finished files are already on this machine and you only want to share them, tick this (`torrent_seed_only`) — existing files are not re-downloaded. A magnet link does not yet have a file list at that moment, so seed-only is refused for magnets; give a `.torrent` through "upload torrent" instead.
- **Choosing files inside**: available once the torrent metadata arrives (a magnet must wait for it; `torrent_meta_timeout` defaults to 180 s and expiring means nobody is seeding right now, which is reported as such). "文件 n/m" changes which parts are fetched (`POST /api/torrent/select`).
- **Tracker injection**: the list is **fetched at runtime** — `bt_tracker_sources` defaults to the two publicly maintained lists, ngosang/trackerslist and XIU2/TrackersListCollection. No tracker is hard-coded in the source or the release archive; the fetched list is stored only in the local `torrent_state/`. `bt_trackers` (your own announces) is ordered ahead of the fetched ones and only http / https entries are taken. With `bt_tracker_auto_update` on, submitting a new task re-fetches any source missing from the cache; **a failed fetch is never treated as "the list is now empty"** — the previous cache stays in use and submitting a task must not die on that step. `bt_tracker_max` (default 30, 0 = inject none) caps **how many are attached to one task**, not the length of the list — aria2 asks trackers one at a time, so piling them on makes the first round slower. `GET /api/bt/trackers` reads the current state, `POST /api/bt/trackers/refresh` forces a refresh.
- **Speed limits and first/last pieces**: `bt_dl_limit` / `bt_ul_limit` (`1M` / `512K`, empty = unlimited) apply to newly submitted tasks only, and the seeding phase takes the upload limit too; a task whose row was changed individually reports that row's value. `bt_prioritize_piece` downloads the first and last 1M of every file first, which is what makes watch-while-downloading previews open earlier.
- **Seeding supervision**: `torrent_seed_ratio` (stop after uploading that multiple of what was downloaded; 0 = do not stop on ratio) and `torrent_seed_time` (stop after that many seconds of seeding; 0 = do not stop on time). With both at 0 a finished task uploads indefinitely and you stop it from the "seeding now" panel (`POST /api/torrent/stop-seed`). Seeding only uploads, it does not occupy download concurrency, and **stopping a seed never deletes downloaded files**. The panel (`GET /api/torrent/seeding`) carries aria2's live numbers — upload rate, peer count, remote seeders, how many trackers are in this torrent — and omits whatever aria2 did not return; it also separates "registered by this program" from "anything else in aria2".
- **Auto-categorisation**: `bt_auto_rules` maps a task to a subdirectory under the global download directory, asking rules top-down and taking the first hit. Each rule first says **what it matches — the name or the link** (`scope`, default `name`) and then contains / regex, so the two kinds can share one table and still never cross over (a link rule is never handed a torrent name to compare, or `https://` would swallow every magnet). Magnets and torrents ask the **name rules first, then the link rules** (`_rule_decide` — the same function drives the real destination and the UI's "test a match", so the two orders can never drift apart); the name comes from the torrent's internal name, the magnet's `dn`, or the file stem, and the tester says which. With no rules configured no directory is invented; a magnet whose filename is not known yet has nothing to match against and is caught by `bt_auto_fallback` (empty = just use the default download directory). The subdirectory is a relative path under the download directory (multi-level is fine), and anything with a drive letter or `..` is pushed back immediately. `POST /api/torrent/rules/test` lets "test a match" try a name, a magnet / torrent, or an ordinary download link in the UI before saving. Rules decide where **later submissions** go: tasks already downloading or already seeding are not relocated, and seed-only submissions keep their own destination. **Link rules also cover ordinary downloads** (YouTube / Bilibili / direct files — the ones with no torrent name to compare), so "magnets by torrent name, web videos by domain" needs nothing more than this one table. The two kinds deliberately differ about the fallback: an ordinary download **never** uses `bt_auto_fallback` (that slot exists because a magnet may have no name yet; letting a plain URL fall into it would move your whole download directory on the strength of one link rule), so a miss simply stays in the default directory — and the tester spells that difference out rather than letting it look like a broken rule.
- **Things that only apply to new tasks have to be said out loud**: trackers and first/last priority cannot be changed on an existing task — aria2 answers "Cannot change option" for `bt-tracker`, and for `seed-ratio` / `bt-prioritize-piece` / `check-integrity` it answers OK while leaving the value untouched. So in the UI only the per-task down / up limit may be described as taking effect immediately; everything else states "applies to new tasks".
- **aria2 error codes are translated one by one**: e.g. code 12 explicitly states that one torrent can only be registered once in aria2, so delete it or stop seeding before re-adding.
- **The byte counts in progress are what aria2 reports for the whole download** (all selected files), not just the main file — for a single-file torrent the two can differ by an order of magnitude.

## Cookies & site logins

Sites that need a login are handled with cookies, either read straight from your own browser or a Netscape-format `cookies.txt` dropped into `cookies/`. A third, optional route is CookieCloud sync — the copy your browser extension already keeps, of which this app becomes just another client (**off by default**). Music-platform login cookies are stored per platform and never leave the machine. There is also a fourth, opt-in behaviour: **"public first"** (`cookie_public_first`, **off by default**) parses without a cookie first and only attaches one when a login wall stops that attempt — see below.

<details>
<summary>Details: browser-read constraints, the YouTube bot check, how the "public first" switch decides whether to attach a cookie, how Douyin's no-cookie responses are classified, the three-state display and merge rules for the three music-platform cookies, where the red "login may be broken" flag comes from and why it does not survive a restart, and how CookieCloud sync writes to disk while keeping the key to itself</summary>

Three ways, pick either:

1. Settings → Cookie → "read from browser" pulls cookies for sites you are already logged into (Chrome must be fully quit for its cookie store; Edge / Firefox need no shutdown).
2. Drop a Netscape-format `cookies.txt` into the `cookies/` directory — it is read by default, no setting to change.
3. Settings → Cookies & login → "CookieCloud sync" → type the server, UUID and key, press "pull from cloud", and the local files are rewritten from the cloud copy (off by default — nothing happens until you fill it in).

Without cookies, YouTube hits the "sign in to confirm you're not a bot" wall (resolution fails, or only 360p is offered). That is a site-side restriction, not a bug.

**"Public first" (`cookie_public_first`, off by default) is about sending your session on every single call.** Before it, any configured cookie source meant *every* parse and *every* download carried it. With the switch on, each URL is first parsed as if you were not logged in, and a cookie is attached to a second parse only when that first one is stopped by a login / member / age / bot-check wall, or only hands back a clipped list (audio and video muxed together). The verdict is kept per URL for 15 minutes and **the download follows the same verdict** — a URL judged "anonymous is enough" does not get a Cookie header on the CDN / aria2 direct link either. **HTTP 429 rate limits, connection failures and "content not found" never trigger a second parse**: a cookie changes nothing for those and the extra call only lengthens the cool-down. What this buys is not a saved request but the fact that content visible to anyone never sees your login state; the price is one extra call for videos that genuinely need a login. The two attempts are **not the same format list** — yt-dlp skips the android/ios clients once a cookie is present — so "the anonymous list is lower" is the normal case, not an error: an anonymous list that parses and is not clipped is used as is, a clipped one falls through to the cookie parse, and if the cookie list turns out lower, the anonymous one wins. One local reading is worth recording: here YouTube's anonymous failure is not a login sentence at all but `No video formats found` (not a single stream), while the same URL with cookies returned 43 streams up to 2160p — so the gate keys on *what the failure looks like*, not on whether the words "sign in" appear, and that shape of YouTube failure does get its second parse. Editing anything in the cookie layer (global source, browser, file path, per-platform overrides, a CookieCloud pull, a Bilibili QR login) invalidates every verdict at once, so an old judgement cannot keep deciding for a configuration that just changed. Per-platform overrides still take precedence over the global source; this switch only decides whether the *first* attempt carries a cookie. The live-**chat** grabber is deliberately outside it (that path keeps attaching the cookie as configured — a members-only chat has no anonymous fallback). With the switch off, behaviour is byte-for-byte what it always was.

Cookie-less Douyin search returns two shapes in local testing: the search API answers HTTP 200 with `{"status_code":2483,"status_msg":"请先登录，再继续搜索吧"}`, and the search page HTML is a ByteDance JS challenge page (`Set-Cookie: __ac_nonce`, body containing `byted_acrawler` / `__ac_signature`). Neither means "this content does not exist". Such cases are now classified as login-required / anti-bot challenge / rate-limited / API error / genuinely empty, with the reason shown in the aggregate search results area and the basis recorded in the log; download failures use the same classification vocabulary. This is identification and reporting only: the program never executes JavaScript handed down by a site and never forges a signature.

The music side keeps its own per-platform cookies under Settings → "音乐平台登录 Cookie" in three separate fields (NetEase Cloud Music / QQ Music / Kugou). Leaving them empty just means the free tier. The NetEase field offers "get by QR", using NetEase's own login QR (confirm in the mobile app, then press "check scan status" to import the session) — no third-party login service is involved. QQ Music and Kugou have **no** QR flow: their QR endpoints require an anti-bot signature, and forging one would cross the line, so you still copy-paste from browser dev tools. Each field reports tri-state "logged in / missing key fields / not configured" based on the keys that platform actually needs and names the missing ones (e.g. "missing token or userid, this source cannot reach member quality"), so pasting a useless key string no longer shows as configured. These three cookies are merged with the global cookie above into one string for the downloader (each platform picks the keys it recognizes); a cookie pasted into the search box overrides only same-named keys and does not evict the saved login. Cookie values are written only into the local `config.json`; logs record key counts, never values, and `cookies/` plus that file are on the packing exclusion list.

The cookie card also **announces when one platform's login state looks broken**: when a download from that platform is judged to need a login, the backend raises a flag in memory, and that row changes from "configured / not configured" to a red "suspected login issue" — hovering states which download decided it, when, and what to do about it, while a summary line at the top of the card says how many platforms are flagged. The row's "clear flag" button calls `POST /api/platforms/cookies/clear-flag`, and re-importing that platform's cookies clears it automatically. The flag (`_LOGIN_FLAGS`) **lives only until the program exits and is never written to the configuration** — it is a fact about the network right now, not a setting — so a restart or a different egress can bring it back, and "the platform flagged yesterday" will not remind you today.

**CookieCloud sync** (`GET /api/cookiecloud` reads this layer's configuration, the last test / pull / push result and the scheme the cloud copy turns out to use; `POST /api/cookiecloud/account` / `/test` / `/pull` / `/push` are the four actions). It speaks the protocol of [easychen/CookieCloud](https://github.com/easychen/CookieCloud), so the address you type may be the official hosted service, a self-built one or a third-party mirror — the whole URL is yours (scheme, port and the API_ROOT subdirectory of a self-built instance included), and the code only strips a trailing slash, so "what gets saved" and "what actually gets requested" are the same string. Both crypto schemes are implemented: **`legacy`** is what the official extension writes (CryptoJS / OpenSSL passphrase mode — `Salted__` plus an 8-byte random salt plus AES-256-CBC, with OpenSSL's `EVP_BytesToKey(MD5)` as the KDF), and **`aes-128-cbc-fixed`** is the fixed-IV one (those 16 hex characters used verbatim as an AES-128 key, IV = 16 zero bytes). Both take their key material the same way upstream does: the first 16 characters of `md5(f"{UUID}-{sync key}")`. With "auto" (the default) the app first tries the scheme the server itself reports in `crypto_type`, then the other one, and only then fails — and the error lists **why each of the two attempts failed**. "Push local → cloud" **overwrites the whole copy stored under that UUID**, so the UI asks for confirmation first, and every other device pulls this new copy afterwards.

What a pull writes: the global file named by `cookie_file`, plus `cookies/<platform>_cookies.txt` for the platforms that actually received cookies in that cloud copy — a platform the cloud copy says nothing about is left byte-for-byte untouched, and one whose file was overwritten has its red "suspected login issue" flag cleared. Each file gets a `原名.bak-<timestamp>` backup beside it before being overwritten, while a file whose content would not change is neither rewritten nor backed up. Nothing else has to be re-pointed: yt-dlp already reads exactly these files. Domain filtering follows the extension's own rule (`.youtube.com` matches `youtube.com`, and `m.youtube.com` matches too); if the filter leaves nothing, the call fails with "N cookies in the cloud, M filtered out" instead of quietly writing an empty cookie file. Shapes that are not recognised get explained rather than guessed at — a third-party client that flattened `cookie_data` into a list is still read, and localStorage carried in the cloud copy comes back as "not useful for downloading, nothing written".

The key stays put: `cookiecloud_key` **can only be written through `POST /api/cookiecloud/account`** (an empty value means "do not change it this time"; `clear_key:true` is the only way to erase it), it is always an empty string in `GET /api/config`, and the password field in the UI therefore never refills itself. A machine token without a session gets a plain 403 on that endpoint — "a token that can write settings" should not be able to flip the switch that decides where cookies get sent. The diagnostics export hides anything whose key name looks like a secret; `cookiecloud_scheme` / `domains` / `server` / `enabled` are deliberately let through (an algorithm name, filter words, a hostname, a switch) while `uuid` and `key` stay hidden — the two are a pair, so hiding one and not the other hides nothing. requests embeds the full `/get/<UUID>` in its connection-error text, so the UUID is replaced by `‹UUID›` before such a line reaches the state file or the log, and log lines print host and port only, never the netloc (embedding `user:pass` in a URL is a common way to write a proxy address). Timestamps, row counts and which files a pull wrote live in the local `cookiecloud_state.json`, which sits on the packaging exclusion list next to `config.json`. Upstream rate-limits 100 requests per 15 minutes, so **nothing polls**: state is read once when the settings page opens and once after each button. Self-test: `tests/cookiecloud_test.py` (never goes online — a real CookieCloud stub server is started from the standard library; the two pinned ciphertexts come from `openssl enc` rather than from the code under test, and the reverse direction is verified too).

</details>

## Network & proxies

Three proxy modes: automatic per platform (foreign through a proxy, domestic forced direct), always, or leave it to the system. Each platform can be overridden individually and the address actually in use is shown.

<details>
<summary>Details: the per-platform proxy table, one-click system proxy and what “reset the network” clears, mirror probing, TLS fingerprinting and the PO Token health gate</summary>

- Three proxy policies: `auto` (per platform: overseas through the proxy, domestic forced direct) / `always` / `none` (leave it to the system).
- 18 sites are recognised: YouTube, Telegram, Bilibili, Douyin/TikTok, Xiaohongshu, Instagram, Twitter/X, Pinterest, WeChat Channels, Xinpianchang, plus Facebook (including `fb.watch` short links), Twitch, Reddit, Vimeo, SoundCloud, LinkedIn, Weibo and AcFun. **That recognition table is the precondition for anything "per platform"**: when a site is not in it, `detect_platform()` can only answer `default`, so every rule written for it silently does nothing and the row never appears in the UI. TikTok and Douyin share one cookie file (both ByteDance) but have opposite proxy verdicts — the first goes through the proxy, the second is forced direct.
- In auto mode, **Settings → Network & concurrency → per-platform proxy** lists each platform and music source with this run's verdict, a manual override (auto / via proxy / forced direct) and the proxy address actually in effect; changes save and apply immediately.
- Reads the system proxy with a "use system proxy" button; "clear and reset network" only clears proxy addresses, per-platform policies and the sniffer list — cookies, history and tasks are untouched.
- **Mirror probing**: `/api/mirrors/probe` speed-tests the built-in GitHub / HuggingFace mirror candidates and picks usable prefixes; when direct access fails, the download tools try the built-in mirrors in order automatically.
- TLS fingerprint impersonation (curl_cffi), optional SSL verification skip, PO Token health gating and the `player_client` fallback chain are all configurable in Settings.

Aggregate search and the music search page use `musicdl` for multi-source search (each source has a time budget; when a source returns 0 items the reason is put on screen), plus lyrics, cover art, tag writing, MusicBrainz lookups and AcoustID audio fingerprinting (`chromaprint/fpcalc.exe` is bundled).

### Cross-platform title matching: the scoring gate

Spotify playlists cannot be downloaded wholesale because of DRM, so the approach is "list the tracks only, then download each title by matching it on other platforms". Which platforms are searched is decided by **music search → parallel strategy → match sources**; the candidate list is identical to "search sources" and every one of them is selectable. The defaults are NetEase / QQ / Migu / Kugou / Kuwo (these resolve addresses on their own CDNs — find it and you can download it). Spotify and Apple are labelled "slow address resolution": their URLs come via third-party conversion services, single tracks do work in practice but take ~10 s each and fail often, so they are not in the default set. The fallback to the default five sources happens only when you specified no match sources at all, and it is stated in the log — it never silently switches platforms.

Deciding "is this the same song" goes through a scoring gate. Beyond three quick criteria there are thresholds: title and artist are **scored separately** — title similarity below 60 means two different songs, artist below 70 means a different person, duration below 25 (roughly 14 s apart) cannot be the same recording; when titles are not exactly equal the duration requirement tightens (below 50 is rejected, about 7 s), and the combined score must clear an 85 acceptance line. Duration acts only as a gate and never adds points — two different songs of identical length is far too common. The two fast paths remain: title + artist equal after normalization and duration inside `min(60 s, max(20 s, 12% of the full length))` (a 30 s clip may differ by 20 s, a 4 h podcast by 60 s); or titles match but artists differ, in which case durations must be near-identical (within 5 s). Version suffixes appearing on the finished file are hard-blocked — you wanted the studio version and the file says `(Live)` / `DJ` / `karaoke`, that is a different recording. The reverse is not blocked (the playlist says Live and the library entry omits the suffix, which is usually the same recording). When several candidates pass, the one with the highest `(score, quality)` wins, so lossy and lossless coexisting yields lossless. Rejected candidates are logged with the reason ("same title «XXX», different artist, duration off by 78 s", "«XXX» duration off by 78 s, outside tolerance", "finished file says live, not the same recording as annotated"), which makes "not found" distinguishable: no such song in the library, a same-title song rejected on duration, or a different artist.

### Single-track links (Spotify / NetEase; QQ is told straight)

The same box behind **解析歌单 / 单曲** takes either a whole playlist or **a single track link**: `open.spotify.com/track/…` (including `/intl-xx/` prefixes and `spotify.link` / `t.spotify.com` short links) and `music.163.com/song?id=…` (the `#/…` hash form is recognised too). Routing keys off `track` / `song` in the path, so `playlist?id=…` on the same domain still goes down the whole-playlist road. A short link costs exactly one GET that reads `Location` — none of the JS the page ships is executed.

Both roads fetch **metadata only** (title / artist / album / duration / cover) and produce the same "pending match" row a Spotify playlist produces; the audio address is resolved at download time by **querying every platform ticked in match sources**, then taking the highest-scoring candidate that clears the gate above; tick order only breaks a tie, and then only when score, tier and quality are all equal — a hit on an earlier platform never causes a later one to be skipped, and no ticked source is reordered or silently dropped. NetEase looks like a detour (its own link goes back out to search and usually lands on NetEase again), and it is not: `api/song/detail` returns metadata without an audio address, and questions like "is this VIP-gated, does this tier serve FLAC" only get answered along the search path. Choosing "逐曲获取高音质地址" does **not** push a single-track link back onto the slow per-track address-resolution road either.

Spotify's persisted-query fingerprint (the sha256) tracks its frontend build. Measured here: the main bundle returns all 81 query fingerprints in one 1.2 s hop, while the 75 chunks it references take 57 s and contain not a single fingerprint — so only the main bundle is scanned, chunks are swept just in case the operation name is missing, and the whole table is cached for 6 hours, so paging, a second playlist and single tracks never pay for it again. If a real fingerprint cannot be obtained the run errors out; a fabricated one is never substituted.

**QQ Music single-track links are not pretended to work.** Without a cookie its three detail endpoints answer empty data / 500003 / 500005 respectively and the page is a JS shell, so the title and duration cannot be fetched; this program does not implement cookie-based QQ single-track parsing. Such a link therefore fails explicitly and says what to do instead — type "title artist" into the search box above, which does yield downloadable rows. QQ **playlist** links are unaffected and still list the whole playlist.

### The keyword match score on a search row

A title search can return dozens of rows with the same song name by different people, and the title alone does not tell you which one to fetch. Each row now carries a 0–100 number next to its source: **how well this row lines up with the keyword you typed**. Above the acceptance line it renders green, below it amber, and a row blocked by a threshold is red with "no match" beside it; hovering the number shows the title / artist sub-scores and the reason it was blocked, and a legend under the header says what the number governs.

It reuses the same comparison helpers and the same thresholds as the scoring gate above, but answers a **different question**: a free-text keyword has no title / artist field structure and no duration to compare, so **duration always reports "not in play"** here, and this score **does not decide "is this the same recording"** — that needs an annotated row with a duration, which is what source switching and duplicate detection use.

How it works: the keyword is split on spaces and punctuation, and **each token** is compared against the row's title and artist separately — the title dimension averages the tokens that hit, the artist dimension is scored once over the tokens assigned to it. Tokens found in neither field are not forgiven: they are folded into whichever dimension went unclaimed and produce their own reason string ("the token 晴天 is not recognisable in this row's title/artist — its artist field says 张信哲"). Mode words (`专辑 / 单曲 / 歌曲 / album / collection`) never participate — playlist search appends 专辑 to the keyword, and leaving it in would drag every album row's title dimension below the line. A row carrying a version tag your keyword did not ask for is flagged the same way: `晴天 (Live) / 林俊杰, 周杰伦` against "周杰伦 晴天" scores **98** and is still blocked because "none of those version words were in what you asked for" — **a high number is not a green light**.

The three sub-scores and the acceptance line (85) live in `MATCH_*` in the backend `music_search.py`, same source as the gate above, and cannot be changed from the UI. Using "switch source" on a row clears its old number and recomputes — the previous row's score does not follow the new one.

### Playlist de-duplication and chunked batch download

When a playlist lists the same song several times, the list merges it into one row marked `×N` after the title (hover states how many entries it stands for, and the download fetches it once). "Download selected" also de-duplicates the manifest before starting, using the same rule (which covers picking rows in separate selections), and names the affected songs in the log (`下载清单里有 1 首重复（同一首歌排了两遍），只下第一遍：「晴天」×2`). The rule is the same as title matching: identical title + artist, then duration inside `min(60 s, max(20 s, 12% of the full length))`. Title and artist normalization flattens case, runs of whitespace and spaces around commas, but **does not strip version words such as `(Live) / 现场 / karaoke`**, so a studio version and a live version are never merged into one row — which would make one of them disappear from the list. Rows without a title are never merged, and rows whose cache entry cannot be found are always kept. The progress total counts the de-duplicated number; skipped duplicates are recorded separately as `dup_skipped`, apart from "no address obtained" failures, and the completion receipt reports the two facts separately.

"Download selected" proceeds in chunks of 6 songs, and each chunk is archived to the location its filename template points to as soon as it finishes — so the file page fills up while the batch still runs instead of at the end. This path does not enter the download queue; progress goes to the operation log (`下载进度 x/N（成功 k 首，已归档 i/j 片）`), and at the end the UI shows a receipt: "multi-select download finished: x succeeded, y had no address, z seconds elapsed" (plus "N were duplicates of the same song and were fetched once" when the manifest was de-duplicated). An error in the middle of a chunk does not void the chunk: already-written files are located on the spot and archived normally (`第 i/n 片中断后从缓存救回 k/n 首`), and the songs not yet on disk are each retried individually (`第 i/n 片逐首重试补回 k 首`), so one bad path does not take down innocent neighbours in the same chunk. The same error line is followed by the last three stack frames with standard-library frames (`os.makedirs` recursion and the like) stripped, so the caller is identifiable. The whole-round budget for title matching is 1500 s, widened to 3000 s when Spotify or Apple are among the match sources (their addresses go through a conversion service, ~10 s per song). Songs never reached before the budget expires are reported separately as "not searched this round" with a remedy (run it again, or use the fast default match sources) and are never merged into "not found by title". Both lists are printed in full in the log (header line, 10 titles per line — not truncated to the first 12) and the UI shows the same lists again at the end under the heading "tracks not matched by title". Before handing work to musicdl, each song's destination is checked: a title starting with `/` or `\` makes musicdl build a path that escapes to the drive root, and its `\\?\H:/` form then fails with `FileNotFoundError [WinError 2]`, taking the whole chunk with it — titles are sanitized here and the file is kept inside the download directory, naming the affected song in the log. A batch runs concurrently and the download library returns finished files in **thread completion order**, so "which file belongs to which song" cannot be positional. It is now resolved by title: the filename (after stripping the " - index (1)" suffix the library adds to avoid collisions, and after normalizing illegal-character replacement and path truncation) must match that row's title; a candidate is taken only if exactly one matches in that directory, and if none matches the song is counted as not downloaded rather than grabbing some other leftover file — the log lists each song whose file could not be identified.

Songs from a previous run still sitting in the download directory are not fetched a second time when you re-run the whole playlist: **"skip already downloaded"** (checked by default), to the right of "N items" in the manifest, scans the audio in the download directory before starting and puts every candidate through the same scoring gate on title / artist / duration. A row judged to be the same song by the same person is dropped from this run's manifest, the full list is written to the operation log with scores, and the receipt and progress line add "N songs already had a finished copy in the directory and were not fetched again". Unchecking it re-downloads. What is compared is the **song**, not the filename (the same track from a different platform usually differs in filename style and bitrate, and old copies stop matching after you change the naming template), and a different extension still counts as the same song (`.flac` on disk versus `.mp3` computed by the template). This directory check additionally requires the artist to match (`require_artist`): the same title by different people is usually genuinely a different recording (original versus cover), so title + duration alone is not enough. Untagged rows have their title guessed from the filename — and while the downloader's default template is "title - artist", the filename fallback splits "artist - title", the exact opposite direction, so those rows are also tried with the parts swapped (tagged rows have a trustworthy direction and are not doubled). To deliberately re-fetch one song use the per-row "download" button — a single explicit action is not bound by that checkbox. Four situations never block and download as normal: the template contains `{id}` or `{source}` (every path is source-specific, so equal names are not the same song), no title can be obtained, the target directory does not exist yet, or the directory holds only sidecar files such as `.lrc` or covers. Archiving no longer creates copies either: if a file already exists at the destination the old one is wholly replaced, and both byte counts are logged (the previous behaviour renamed to `title_1.mp3` and kept two).

If the address a row got on platform A will not download, or you want another platform to get lossless, use the row's "switch source"; for bulk edits use the toolbar's "switch source for selected". The backend re-searches the other match sources and **rewrites the row only if the candidate passes the scoring gate and the new address probes successfully** (no probe result means the row is left alone). A failed switch states in both log and UI whether title, artist or duration blocked it, and unmatched tracks are listed once more at the end of the batch. Rows produced by the local scan and "lossless reference" rows refuse this operation outright with a reason: the former is already a file on disk, the latter is metadata only — neither has an "alternative source" to switch to.

A row labelled Spotify may actually have been pulled from YouTube. This used to be visible only in the log; now the source column says so: such rows carry a "converted" marker, hover shows the full chain (`Spotify → YouTube`, `Spotify → spotsaver`), and the download log records that real route as well. The adjacent "block re-uploads" checkbox (off by default) is about something else: when on, a fetched file that does not match the row you clicked (different title or artist, or duration off by more than 3 s) is not downloaded, is logged on the spot and is listed at the end. Mind its boundary — it does **not** block "fetched from another platform via a conversion service" as such: Spotify and Apple have no official audio path at all, so blocking that category would mean a playlist downloads nothing. Only metadata mismatches (a re-upload of a different recording) can be caught, which is why it stays off by default.

### Local library and snapshot index

With "include local library" ticked, search results also include songs already in your download directory. This path now reads the **tags carried by the file**: everything mutagen can give (title / artist / album / duration / bitrate / sample rate / bit depth / embedded cover / embedded lyrics / tag type) is taken in one pass, ffprobe is consulted only for what it cannot give, such as bit depth, and filename guessing is the last resort — each row is marked as tag-derived or guessed. Parse results are cached by "path + byte size + mtime", and the whole scan index is stored as a **snapshot** under `local_index\` in the program directory, one file per scanned directory (the name is a hash of the directory path, so indexing several download directories never overwrites each other). **Nothing is written into your download directory any more**; a `local_music_index.json` left there by an older version is moved into the program directory on first read and the original deleted, and its records are reused rather than re-parsed. Search uses snapshots younger than 5 minutes by default: a hit is returned immediately without even walking the directory. When the snapshot is stale, the **previous snapshot is handed to the UI first** (thousands of songs still open in milliseconds) while the re-scan runs on a background thread, one thread per directory at a time, so the next query gets fresh content. Moving a file computes its age from the file's original mtime, not from the moment it was moved, so an index made an hour ago is still correctly recognized as stale. To rescan right now press "scan local library" — it bypasses the snapshot, and the result states how many songs were found and where the index file is; if the background is scanning that same directory at that moment, the button joins that run and waits for it (up to 90 s) instead of returning numbers you already see. Ordinary searches and the "skip already downloaded" check never wait on a scan. The "skip already downloaded" check ignores snapshots and rescans current disk state every time, so a song that just finished cannot be hidden by a stale snapshot and re-downloaded the next day; after a batch finishes, the snapshot is refreshed in the background. All these differences matter more as the library grows.

There is exactly one place to listen: clicking "preview" on a music result row or a favourites row puts the controls in the **persistent bar at the bottom of the window** (current title and artist, cover, progress bar and time, previous / play-pause / next, volume and mute, close). Switching pages does not hide it and does not restart playback in a new player. The spacebar toggles play/pause, except when focus is in an input, textarea or select, when it is on a button or link, or when any dialog is open. When a track ends the next one in the same list's queue plays automatically; with no next item it stops. At the end of a batch download, songs blocked by "skip already downloaded" are listed row by row in a dialog: title → the filename already in the directory, with the matching score and the title found there, ending with the hint to uncheck "skip already downloaded" above the manifest if you wanted a re-download.

### Quality requirements and the lossless reference

With "lossless reference" ticked, every search additionally queries the Qobuz / Tidal official catalog metadata once: title, artist, album, exact duration, ISRC, bit depth and sample rate, lossless flag, official link. What local results lack most is "how long should this actually be, and is there a lossless version", and musicdl's own Qobuz / Tidal sources require account tokens — logged out they return 0 items — so this path supplies exactly that one thing. **It stops at metadata**: the audio step sits behind a third-party human-verification gate that was put there deliberately, so the program does not obtain verification tokens, does not bypass the check, and does not touch any credentials. Such rows are easy to spot: the source column reads "Qobuz·ref", hover lists ISRC, bit depth/sample rate, exact duration, version note, release date and label, always ending with "read-only, audio is not downloaded from this row", and the action column is "official page" (it opens only the platform-provided official link). They cannot be selected and never enter the download or matching path.

The **"quality requirements"** dropdowns in "parallel strategy" (format / bit depth / sample rate / bitrate) plus "do not download below spec" do three things that are possible, and the one that is not possible is stated first: **this layer cannot pin which tier a platform hands you** — each source's quality tier is a constant hard-coded in musicdl's source classes, and when building a client the only things you can pass are search size, retry count, working directory and cookies; there is no entry point for "give me 24-bit". So the requirement does not pretend to pin anything; it does exactly three things: (1) when several platforms have the same song, the tier that meets the requirement is ordered first; (2) with "do not download below spec" ticked, a song whose **platform-declared tier is confirmed below** the requirement is never handed over, and the log names the song and which dimension failed; (3) after a file lands, its **own tags** are read to verify the actual tier, which also catches a lying label (a 128k MP3 wearing a flac name) — the verdict is appended to that row's "downloaded" log line and listed again at the end of the batch. Two rules are fixed: if a dimension **cannot be read, that dimension does not disqualify anything** and is reported as "not verified" (otherwise every source that does not self-report would be skipped by "lossless only", which would treat "unknown" as "failed"); and **lossless files are not judged by bitrate** (16-bit/44.1 kHz flac is already above 900 kbps, platforms often do not report a bitrate for lossless, and gating on bitrate would classify the best tier as failing). With "lossless reference" ticked, each result and each finished file is also compared against the Qobuz / Tidal row on bit depth / sample rate / lossless — again metadata only, no audio at all. That comparison passes the same scoring gate first: if the reference row's duration does not line up, the verdict is "no comparable reference" rather than "below reference", because that is a different recording, not a lower quality, and the conclusion carries the reference ISRC so you can check the official page yourself. The tier tables exist in one place in the backend and the UI renders them from the status endpoint, so the two cannot disagree. To re-check files already on disk, open the resource library and press "verify quality": every audio file in the current filter has its own tags read, and the verdict hangs on that row's "quality" column (below requirement / meets / not verified / file missing), with a summary line above the card giving counts. That endpoint accepts only paths inside the download directory; one out-of-bounds path rejects the whole batch and states where the directory is.

"More → fingerprint" on the file page uses the bundled `chromaprint/fpcalc.exe`, so you do not need to add it to PATH ("add to PATH" only affects terminals opened afterwards; a running service will not pick it up). The settings field wants the **application** client key (registered at acoustid.org); the user API key you see after logging in is rejected by AcoustID as `invalid API key`. Missing fpcalc, a rejected key, and a file with no audio track all produce an immediate dialog on click instead of "fingerprinting…" followed by a buried log line.

### Which layer the "embed cover art" tick actually reaches

"Write the cover into the audio file when the download finishes" (`embed_cover`, on by default) governs **the picture inside the finished file**, not "whether to tag it at all": unchecked, the title / artist / album / lyrics text tags are still written, and the same-named `.jpg` stays beside the file with not one byte touched.

- **Checked**: after writing, the file's own tags are read back and the verdict is logged per track (embedded, or not embedded with the reason named), and the tracks that did not take it are called out separately in the music summary.
- **Unchecked**: only the same-named image file is left beside it, no cover goes into the file, and **the picture the downloader itself had already written into the tags is taken back out too** (`strip_embedded_cover()`). This layer had to be added: musicdl runs with `auto_supplement_song` on by default and writes the cover into the file before tagging, so "we do not write it ourselves" only covered half the path — there was a time when the box was unchecked and the finished file still had a picture in it. Now mp3 loses `APIC`, flac loses `PICTURE`, m4a / mp4 loses `covr`, and **only the tags change — nothing is re-encoded** (measured on the same song in both arms: the audio frames are byte-for-byte identical). Containers where the cover is not a tag-level field are left alone and the log says it was left alone. If the tags were changed but a picture still reads back, that track counts as a failure and is named one by one ("you asked not to embed it, but the picture in the file could not be taken out"), the log line is raised to warning and the music summary gains "could not take the cover out of {n} track(s)" — no simulated success.
- **One difference stated as measured**: taking the picture out of an mp3 also shrinks the tag area, so the file gets smaller; taking it out of a flac does **not** reduce the size — mutagen fills the freed slot with all-zero PADDING (verified byte by byte that it is not leftover image data), so this is not a promise that "the file returns to its coverless size".

### Favourites list and filename template

Clicking "favourite" on a search result row accumulates songs found across platforms into your own list: the manifest card supports whole-list download, per-row and bulk source switching, and remembers tracks that were not found last time. The list lives in the local `music_favorites.json` (never packed into a shared archive), and rows are identified by "title + artist + duration", so storing the same song twice merges into one entry. Each row also owns a cache slot: a song added from the same search round has the real result living in that slot, so a whole-list download fetches it as-is; when the slot is empty (the service restarted, or the cache cap evicted it) the address is re-found by title at download time, and if that fails the row is marked stale. Staleness has two distinct causes with two remedies: "not matched by title in the match sources — switch source, or add that platform's login first before downloading this list", and "the whole round timed out and this track was not reached (this is not 'not found') — just download it again".

The **filename template** accepts `{name}`, `{artist}`, `{album}`, `{source}`, `{id}`, `{ext}` plus the archival fields `{track}`, `{disc}`, `{year}`, `{date}`, e.g. `{artist}/{album}/{year}/{track} - {name}` — the directory layout Emby / Jellyfin-style libraries read. Track numbers are zero-padded to `01`, otherwise a library sorts them 1, 10, 11, 2; `{track}` prefers the platform's own track number (key names differ per platform: NetEase hides the release date inside the album's millisecond timestamp, QQ puts the track number on the entry itself), falling back to the row's position in the playlist. Fields with no value stay empty: empty directory levels are not created, a dangling leading/trailing "- " is trimmed, and a mistyped placeholder (`{track_no}`) never appears literally as braces in a filename. Dates accept `2005-01-01`, `2005.1.1`, `2005年1月1日`, `20050101` and second / millisecond timestamps; anything unrecognized stays empty rather than producing a weird folder name.

## Subscriptions

RSS, web-page changes, Telegram channels and music playlists are managed on one page; each scan enqueues only entries that are new. Rules can be set per subscription, and blank means follow the global setting.

<details>
<summary>Details: rule fields and when they apply, how scans are logged, why the sync-plan preview touches neither the queue nor the cursor, where entries deleted upstream go, why the playlist cursor is keyed on title+artist+duration, and why new entries are not marked read while a batch is still running</summary>

RSS / web-page / Telegram channel / music playlist sources are all managed on the "subscriptions" page (there is no separate screen any more). Top-left is the "add subscription" card (paste a link, detect the source type, choose how Telegram is read); top-right is the "tracking & scan" card with "scan all now", the "auto-download new items" switch and a `共 N 个 · 已启用 N` counter; the full-width card below is the list itself. Each subscription can carry its own rules: content type (long video / short video / live / audio-podcast), duration range, must-contain and exclude words, date window, quality and naming template, audio-only, and a maximum number of items per run. Blank means follow the global setting. Rules apply only to entries that appear after they are set; the operation log states for every scan how many were downloaded, how many were blocked and why. `sub_first_download_n` controls whether a first scan also fetches the most recent N items (0 = record IDs only).

**A plan before the scan**: `POST /api/subs/preview` answers "what this round intends to do" — how many entries were read, how many are unread, how many would be enqueued under the current rules, and which rule blocked which ones; the log writes those three facts separately. **It is a pure dry run**: nothing is enqueued, the `last_ids` cursor does not move, and nothing is written to disk, so after pressing preview the queue holds exactly as many tasks as before and no entry has been marked read because of it. Previewing or listing the archive of a subscription that does not exist answers 404 on the spot.

**Entries deleted upstream no longer vanish**: the comparison basis in `_feed_sync` became "the batch read this round = next round's baseline", so when an entry disappears from the source it goes to the archive (`POST /api/subs/archived`, clearable with `POST /api/subs/archived/clear`) instead of simply being gone; the archive holds `SUB_ARCHIVE_CAP=100` entries per source and drops the oldest beyond that.

The subscriptions table and the history table used to let their content decide column widths, so long links pushed them past 1500 px inside a ~1100 px container and the "actions" column fell off-screen. Both now use one shared variant (`table-layout: fixed` plus ellipsis on overflowing cells) with column widths declared per table: titles and links truncate, the full value stays in the hover `title`, and at 1440 and 1280 the measurements came back "container width == table width" — no horizontal scrolling. The new sync-plan tables use the same variant. At 1024 horizontal scrolling is still needed (see [Known limitations](#known-limitations)).

Music platform playlist links (NetEase / QQ / Kugou / Migu / Kuwo / Spotify / Apple and similar) are recognized as "music playlist" sources: each scan re-fetches the whole list and downloads only newly appearing tracks. Cursors for these sources key on "title + artist + duration", so the same song listed by another platform is not downloaded twice. Some platforms in "list titles only" fast mode give only a title per row (no artist, no duration); in that case a hash of that row's link is appended to the key so that two different songs sharing a title (an original and a remix) are not merged into one entry. Rows that carry only a title have no audio address, so the program re-resolves them by title against the match sources instead of dumping them into the general download queue. Each round looks at 300 items and the cursor stores 300 (songs must not be permanently missed because the window was too narrow). Entries of this kind always count as "audio/podcast", so ticking only "long video" in the content-type rule blocks the entire playlist every round. Batch music has a single channel in the program: if the previous music batch is still running, this round's new songs are **not marked as read** (marking them would leave nobody to fetch them) and the log says "will be picked up next scan". Title matching may also find nothing at all (no such song in the match sources, or a row that only has a title to go on); the log lists every unfound track in full, but those rows are still marked as read and will not be retried next round — to retry, either make the playlist spell that row differently or change the match sources and press "scan now". These sources have no reliable per-track publish time, so "backfill by date" speaks for the whole playlist when no date window is given, instead of pretending a window applied.

</details>

## Subtitles & AI processing

Site subtitles can be embedded per language or saved as a sidecar `.vtt`; local transcription, glossary checks, bilingual export and the four-stage AI pipeline all live on this path. After machine translation the output can additionally be **checked line by line for suspicious results**, and the subtitle itself edited in the sentence-by-sentence proofreading panel.

<details>
<summary>Details: language-code matching, diarization and timestamp seeking, the SRT / VTT / ASS trio, stage artefacts on disk with single-stage re-runs, the ten post-translation checks and the reflective fix pass, the three timeline dimensions and why "not computed" is not "switched off", the sentence editor's backup and 409 gate, the hardsub entry point and output naming</summary>

- Site-provided subtitles are embedded per language you tick (exact language-code matching), and can additionally be saved as sidecar `.vtt` files.
- Local transcription: faster-whisper (with speaker diarization, voiceprint-clustering variant); clicking a timestamp in the transcript seeks to it.
- Glossary / custom dictionary verification of translated terms, smart subtitle line wrapping (max characters per line `subtitle_wrap_width`, default 16; max lines per cue `subtitle_wrap_lines`, default 3), bilingual export as **SRT / VTT / ASS**.
- **AI pipeline**: subtitles → polish → summarize → translate, four stages, each artifact persisted and individually re-runnable (`/api/ai/pipeline`).
- **Post-translation checks** `POST /api/subtitle/qc` (switch `subtitle_qc`, on by default): every line is compared against its source for ten kinds of suspicious output — no translation / not translated / still in the source language / suspected omission / suspected padding / term not per glossary / numbers do not match / suspected repetition / over the per-line limit / style tags lost. One call inspects at most `QC_ROWS_CAP=200` lines and **the findings only go to the operation log — the subtitle file is not touched**. The suspicious lines can be handed back to the chat model for one more pass (`subtitle_qc_reflect`, off by default because it spends more tokens, `REFLECT_CAP=80` lines per batch): when lines are merged into a paragraph **only numbered lines are accepted**, and if the numbering cannot be parsed the first-pass translation is kept — better to change nothing than to copy the model's commentary into the subtitles. "Over the per-line limit" and "style tags lost" are not something a reflective pass can fix; they belong to the two tools below.
- **Re-wrapping by characters per line** `POST /api/subtitle/rewrap`: already-translated subtitles are broken into lines again using those two Settings values, without re-running the translation.
- **Sentence-by-sentence editor** (file page, "逐句校对"): `GET /api/ai/srt` reads a subtitle (or the media file next to it) and returns each cue's index / start / end / speaker / text plus the file's `mtime_ts`, for both `.srt` and `.vtt` (milliseconds scale by digit count; writing back to `.vtt` keeps the `WEBVTT` header and dot-separated times). Nothing touches the disk until you press "save" (`POST /api/ai/srt/save`), and **the save first writes a `原名.bak-<timestamp>` backup next to the file** (back-to-back saves inside one second never overwrite each other — collisions get `.1 / .2`). Empty text lines are skipped and reported as `dropped`, an end earlier than its start is floored to 40 ms, negative starts clamp to 0; speaker markers survive the write-back, and a selected line can shift forwards / backwards (its end is recomputed from start + duration), merge with its neighbour, or be deleted. **If the subtitle was rewritten by the pipeline or another window after you read it, saving returns 409 and names the file and the moment of that rewrite**, so the UI makes you re-read instead of overwriting freshly generated content — callers that do not send `base_mtime` are not subject to this gate. Shifting a whole track still goes through the existing timeline calibration.
- **Timeline checks, three dimensions** (the `timeline` field of the same `POST /api/subtitle/qc` response — it shares the `subtitle_qc` switch but **needs no second track**, so it computes on a single-language subtitle too): **coverage** = union of cue spans ÷ media duration (a union, because roll-up site captions legitimately overlap and summing would exceed 100%; under 35% only raises a hint — instrumental and wordless passages are supposed to be empty) · **largest gap** = the longest silence between cues, warned above `QC_TL_GAP_WARN=30` seconds; the silence before the very first caption counts too, the tail gets a tolerance band of 8% of the duration (floor 10 s, ceiling 90 s) and whatever follows the last cue is always reported separately and never counted, and overlaps are only tallied, not flagged · **reading speed** = display width ÷ display duration, capped at 9 units per second for CJK and 14 for latin (the same `text_units` the wrapper and the "over the per-line limit" check use); cues shorter than 0.4 s go to a "too short" list, cues shorter than 0.1 s are treated as layout artefacts (the 0.01 s duplicate flash cues sites emit) and excluded, and inline VTT tags are stripped before counting. Two further **report-only** lists: cues whose entire text is a filler, and the same line repeated three or more times in a row (Whisper does this over silence and end-credit music; a song chorus genuinely repeats). The UI offers "drop these N lines by name" — it asks for confirmation, edits only the copy on screen, and writes nothing until you press save. Freshly transcribed subtitles get the same pass (`_qc_report_written`), log only. **When the duration cannot be obtained, coverage and the tail item honestly return `available: false` with the reason — "this was not computed: … (missing input, not QC switched off)"**; conversely, with `subtitle_qc` off the pipeline now logs "subtitle QC is off … an absent QC line does not mean it was checked and clean" instead of going silent. Each list shows at most 8 entries while the counts stay exact, and the UI says "the other N lines are not listed here". Self-test: `tests/timelineqc_test.py`.
- **Hardsub burning**: file page, per-video "more → burn subtitles" — pick subtitles and styling and you get `name.hardsub.mp4`; the source file is untouched. Which encoder draws it is decided by "Settings → video encoding"; if the preferred encoder fails on the real file it falls through to the next one from scratch, and the half-written output is deleted first (see [Video encoding & transcoding](#video-encoding--transcoding)).

</details>

<details>
<summary>Details: why separation wants its own environment, the two RoFormer weight families and the Demucs shortlist, the three device settings and how "actual device" stays honest, the five messages that name which layer is missing, the five analysis metrics and the 180-second sampling rule, why the second layer (beats and structure) keeps the old reading instead of replacing it, why everything is downmixed to PCM first, the pre-flight checks before a thread starts, the bundled fpcalc fallback and the client-key trap</summary>

- **Two families, four RoFormer weights to choose from**: BS-RoFormer ×2 for vocals, Mel-Band RoFormer (works for vocals and accompaniment), plus Inst V2 trained on the accompaniment. "Download weights" fetches them one by one, **each verified against its sha256 — a mismatch discards that file instead of calling it downloaded** — and resumes a broken transfer. The package's own model list names 84 further community models that are only a registry, with no reachable download source, so they get no option in the UI; on the Demucs side only the four names verified on this machine are offered (`htdemucs` / `htdemucs_ft` / `mdx_extra` / `htdemucs_6s`) — names that do exist in its registry but were never actually downloaded and run on this machine are left out too, because offering one is handing the user a button that reports "the model could not be fetched".

A weight name outside the table, or a device outside the three, is refused on the spot with the accepted list named.
- **"Why separation does not work yet" names the missing layer**: no environment, no `separator_runner.py` entry script, the package failing to import inside that environment, a weight missing its ckpt or its yaml, GPU chosen with no CUDA visible — five different sentences on screen with five different remedies (the first two: press "build the separation environment"; the middle two: press "download weights"; the last: switch device yourself, or install the driver).
- **How to use it**: the row's "more → separate vocals" on the files page opens a small chooser first — **engine / model / stem range / device**, all four prefilled from Settings, and what you change there applies to this run only. The voice page card stays the home of the defaults; starting a job from here never writes back to Settings. Once it starts, the button becomes "open the mixer" and carries this file's path across. The finished files land in `separated/` (RoFormer) or `demucs/` **beside the source file**, and each path is written to the run log.
- **The mixer has an entry point on the files page too**: for a file that has been separated, the "mix stems" menu item jumps to the mixer and reads the stems back at once — no copying paths by hand.
- **One copy of the model list**: the four Demucs names come back from `/api/ai/voice_status` and both dropdowns render from it — a second copy in the UI drifts from the one the save gate checks, which would then mark the app's own option illegal. This also caught a real bug: that reading used to be fetched only when the voice page opened, so a user who went straight from the files page to the chooser saw an empty model field (the selection had degraded to a bare id). Opening the chooser now fetches it.
- **Stem mixer** (a card on the voice page): it reads back the stems from the last separation and gives each one mute / solo / volume plus a localised name (vocals, drums, bass, other, guitar, piano), plays them together and can loop the whole thing, then exports the balance you dialled in. The summing runs through the local ffmpeg (`amix` with `normalize=0` - left on, every stem is divided by the track count and the balance you heard is not the file you get); muted stems never reach the command; output is WAV (`pcm_s16le`) or MP3 (320k), written next to the first stem with a `-mix-` timestamp, and the card attaches a player to the result. The fader stops at 100% on purpose: preview goes through `element.volume`, which cannot exceed 1, so a slider that offered 200% would be lying.

**Muxing audio tracks** is on the file page under "more → mux audio" (only video rows offer it): it muxes several audio files into that video as one multi-track mkv, and the video stream is never re-encoded. The dialog first lists the audio **next to this video** - its own stems (the layer under `demucs/` or `separated/`) plus audio files in the same folder, each tagged with where it came from - and a second column browses the download folder for anything else. Every picked track gets three fields: language (nine choices, written into the mkv `language` tag), track name (what the player shows in its track list) and codec (auto / copy / opus / aac). Up and down arrows set the track order of the output, the "default track" field decides which one the player opens with, and every other track has its default flag explicitly cleared. The result is written as a separate `name.mux.mkv`, and an existing file with that name needs a confirmation before it is replaced. Four decisions worth stating:

- **mkv always.** mp4 cannot carry PCM from a wav or an opus track, so rather than adding a container decision we pick the container that fits.
- **Lossless tracks are re-encoded once by default.** Copying wav / aiff / ape into mkv leaves whole PCM behind - about 30 MB for a 3-minute track - so the default is 192k opus; set that row to copy and nothing is re-encoded.
- **No count, no go.** The new tracks' stream indices start after the number of audio tracks the source already has, so when ffprobe cannot answer, the dialog says it cannot tell and points at FFmpeg instead of assuming 0 - assuming 0 would paste the language and track name onto the original track and still report success.
- **mov_text subtitles are refused by mkv.** When that happens the subtitle track is dropped, the remux is retried without it, and both the run log and the completion message say the output carries video and audio only, instead of quietly losing a track.

The offline suite is `tests/audio_mux_test.py` (46 checks, temporary directory only, ffmpeg stubbed); a second live pass builds an mp4 with a mov_text subtitle, muxes a wav and an mp3 into it with the real ffmpeg, then reads the result back with ffprobe to check codec, language, track name and default flag track by track.

**Audio analysis** is on the file page under "more → audio analysis": librosa reports BPM, key (Krumhansl style-correlation matching), loudness in dBFS, spectral centroid and total duration. The result is written to the operation log and to a sidecar `name.analysis.json`; only the first 180 seconds are used by default so long videos do not eat memory. Audio is always extracted to 22050 Hz mono PCM via ffmpeg first, so `.mkv` / `.mp4` and `.mp3` are treated identically. Before spawning the thread, the file header is probed with ffmpeg: files that yield no media info (an image or a script picked by mistake) or have no audio track at all fail immediately with the reason in the dialog, instead of answering "analyzing" and burying the failure in the log. The same applies when librosa is not installed — instant error, pointing at "Components & dependencies".

**A second layer in the same cell: beats and song structure.** It appears once installed, and when it is not, only these two items are missing. Output joins the same JSON and the same log line: `bpm` / `beats` / `downbeats` (beat-this), `segments` (with labels such as `intro` / `verse` / `chorus`, all-in-one), `bpm_allin1` (the structure model's own BPM), `analysis_device` (where it actually ran), `analysis_note`, `analysis_error`. Three 口径 decisions matter here:

- **The old reading is not replaced silently.** librosa's tempo fails by a factor on half- and double-time: a synthetic 180 BPM clip came back as 89.1, the real song 說好不哭 is 76 and got 152, Brave Shine is 85.7 and got 112.3, while the two neural sources agree within 1% on the same files. So `tempo_bpm` and `bpm` each keep their own number, and only past a 25% difference does the log gain `旧读数 112.3（相差 0.76 倍）` - both numbers stay on the table for you to judge.
- **Beats and structure read the whole track; the librosa cell stays capped at 180 seconds.** Structure is meaningless without the full song, and the comment says the two windows differ instead of pretending they share one 口径.
- **Whichever layer is missing is the layer that gets named, and no subprocess starts.** Packages not installed, models not filled in, environment absent are three different sentences; one broken model costs that item only, never both.

This layer uses two packages (`all-in-one-infer` and `beat-this`) installed into the same `tools/separator/venv` as separation, reusing its torch, and it is its own row under "Settings → Components & dependencies": **the two packages** join upstream version detection and the one-click batch (like audio-separator / demucs), while **the two model sets** only report presence and get a "Install analysis packages + models" button - they stay out of the one-click batch, because 8 structure folds (~11 MB) plus a 77 MB beat model should not be spent by an accidental click. "Is the model present?" asks **the installed library itself** whether it can resolve the file (`local_files_only`), and each file's pinned sha256 must match: the cache layout and the resolution rules belong to that library, so anything it cannot see counts as absent. The beat weights' author host measured as a site-wide 503 this round, so the only reachable source is a third-party mirror - which the UI says out loud ("not the author's release, verified against a pinned sha256") rather than passing it off as official. Timing on this machine (a real 252.3 s song): about 56 s on GPU, about 94 s on CPU for a 180 s clip.

### Receiving cat-catch pushes

The third-party sniffing extension [cat-catch](https://github.com/xifangczy/cat-catch) (GPL-3.0) has no server-side interface: you can only make its "settings → send data" POST sniffed resources to an address you fill in. In the UI it is the "sniffing → receive cat-catch pushes" card, where the "send data URL" and "request body template" fields are copied into cat-catch (choose POST as the method). The card also shows cumulative receptions, items blocked by rules, and pending decryption keys.

- Integration follows only the request-body shapes stated in its public documentation; **none of its code is used**. The docs themselves say the feature is still experimental and JSON shapes differ between versions, so `data` is accepted as an object, an array, stringified JSON or a bare link; anything unrecognized is named in the operation log.
- `referer`, `cookie` and `userAgent` in a push are attached to that task as-is (HLS goes to `N_m3u8DL-RE`, split Bilibili audio+video goes to the merge path, everything else to the general queue). AES keys arriving via the `addKey` action are stored per tab for 1 hour, and m3u8 pushed from the same page automatically picks them up (`--key` / `-decryption_key`). Rules are stored in `catcatch_rules.json`, can be disabled or deleted individually, and are on the packaging exclusion list.
- A push contains the site's login cookies, so the "send data URL" should only ever be `http://127.0.0.1:8765/...`; do not point it at an external address. The card states this too.

## Video encoding & transcoding

For actions that re-encode video — 「转码」 and 「烧录字幕」 on the file page and in the library — which encoder runs is now decided by three drop-downs in Settings: CPU x264 / x265, or hardware HEVC on NVIDIA / Intel / AMD. **The default is `CPU` + `x264` + `medium`, which is exactly what this feature has always done** — don't touch the setting and nothing changes; GPU encoding and x265 both need an explicit choice.

<details>
<summary>Technical details: why probing has to encode a real frame, how the per-vendor parameter names are reconciled, `-tag:v hvc1`, the x265 timeout multiplier is measured, how the fallback chain is ordered and why the two CPU entries are never dropped, why a half-written output is deleted first, and why VAAPI is not in this round</summary>

- **The hard-coded libx264 in the presets is gone**: the `mp4` and `mp4_1080` entries in `TRANSCODE_PRESETS` get their video-encoding segment swapped for whatever the current settings produce, before running; every other argument (`-vf scale`, the audio flags) is untouched. The `-c copy` remux and audio-extraction presets don't re-encode video, so this setting doesn't affect them at all; 「FLV/TS → MP4（优先 copy）」 still tries copy first and re-encodes with the current encoder only if that fails.
- **One function owns the parameter mapping** (`_encoder_args()`): the settings layer exposes a single "lower = more bitrate" CRF number, and each vendor spells it differently — x264 / x265 use `-crf`, nvenc uses `-rc vbr -cq N -b:v 0` (without `-b:v 0` it ignores cq), qsv uses `-global_quality`, amf uses `-rc cqp -qp_i / -qp_p`. nvenc's preset names come from a separate table (veryfast→p1, fast→p2, medium→p4, slow→p5). **HEVC in an mp4 always gets `-tag:v hvc1`**, otherwise QuickTime and some players can't recognise the track.
- **Probing must encode a real frame**: a name appearing in `ffmpeg -encoders` doesn't mean it works. When 「探测编码器」 is clicked under Settings → video encoding, every candidate is fed one 320×320 black frame into `-f null`, **with a hard 8-second timeout**. That isn't caution — the three typical failure modes differ: an out-of-date NVIDIA driver reports `Driver does not support the required nvenc API version` (the UI translates it into which version is required and which driver is installed), Intel reports `The current mfx implementation is not supported`, and AMD's AMF in some states **never returns at all** — without that hard timeout, probing would freeze the page. Results are cached for 10 minutes: entering the Settings page pulls them automatically, and the button is the forced re-probe (**click it once after upgrading a driver or swapping FFmpeg**). Every row shows "available / unavailable + reason" — no blanks.
- **The fallback chain**: `auto` tries NVIDIA → Intel → AMD → x265 → x264 in order; naming a vendor puts that vendor first with the two CPU entries behind it; `CPU` means x265 and x264 cover for each other (an FFmpeg build without libx265 shouldn't make the whole job fail). **Encoders the probe says it can't do are dropped from the chain outright**, so nothing waits for a guaranteed-to-fail encode; `libx264` / `libx265` are never dropped and the chain is never empty. The 「降级链」 line under the card shows the order produced by the **saved** settings — change a drop-down, save, and it updates itself.
- **x265 gets 3× the time budget**: same machine, 1080p30, the same 30-second excerpt, CRF 23 / preset medium measured `libx264 4.3s` vs `libx265 11.9s` (**2.75×**; 3.6× on the synthetic noise source). On a slower box the same budget would kill x265's own run, so that attempt's budget is tripled. When it does get cut off, the log says "the encode ran N seconds and was cut off (an encoder this slow means you should pick a faster preset)" instead of failing silently.
- **On failure, restart — don't leave a half-file**: switching encoders means encoding from scratch, and a file left half-written looks like a finished output, so each switch deletes the previous attempt first. The log records per attempt "X didn't work (the FFmpeg error collapsed onto one line), retrying with Y", and the completion line names the winner (e.g. `烧字幕完成: xxx.hardsub.mp4（42 MB · 用 H.265/HEVC（AMD 硬件 AMF））`). Clicking 「停止」 is not an encoder failure and won't retry.
- **Not in this round**: Linux VAAPI — it needs `-vaapi_device` plus `hwupload`, which rewrites the filter chain and collides with the `ass=` subtitle-burn-in filter.
- Settings and API: `video_encoder` (`auto` / `cpu` / `nvidia` / `intel` / `amd`), `video_cpu_codec` (`x264` / `x265`), `video_cpu_preset` (`veryfast` / `fast` / `medium` / `slow`). Anything unrecognized is rejected with a 400 naming the allowed values, and it will never silently switch you to another vendor; readings come from `GET /api/video/encoders` (`?refresh=1` forces a re-probe).

Without it the app still works; you just get the old "Traditional does not match" behaviour. `librosa` is what "audio analysis" needs (it pulls numba / llvmlite). `cryptg` is optional, but without it telethon falls back to pure-Python cryptography and Telegram operations become noticeably slow — those two startup log lines `Failed to load SSL library` / `cryptg module not installed` are exactly that (portable packages from v1.2.8 onwards bundle cryptg, so no install needed).
- **The PO Token row is two layers**: pressing "install" on the `bgutil-ytdlp-pot-provider` row installs the **plugin layer** (`yt_dlp_plugins/extractor/getpot_bgutil*.py`, what yt-dlp mounts the token on). The **service layer** — the bgutil POT server that actually mints tokens — ships inside `tools/bgutil-pot-server/`, and `pot_daemon.py` starts it with the local `node` whenever the probe finds the port empty; the program does not bundle a node binary, so the only thing that can keep it down is a missing `node` on PATH, and the small line under the row says exactly that. So the row turns green only when all three are in place: plugin installed + the "PO Token service gate" switch in Settings is on + that address answers `/ping`. Whichever layer is missing, that line (`_pot_component_note()`) names it — with the switch off it says "while it's off no token is fetched", never "nobody is answering" at a switch that is already on, and vice versa. Once all three are in place it says something else: 4K needs **both the token and a client that spends it (`all`)**, and when a list comes back with no video-only track the parser re-resolves with `all` by itself (see the [FAQ](#faq)). Because what is missing is usually the service rather than the plugin, this row is excluded from "update all" (`skip_all`, dropped from the batch in the UI) — no point nagging every boot to install a package that still cannot fetch a token. Whether the plugin is installed is no longer guessed from the pip distribution name: `_pot_plugin_installed()` looks for the three plugin modules yt-dlp actually loads (no module matches the package name, and probing for one reported "not installed" even after a successful install).
- **Three versions per row**: `current` = what the running process uses; `bundled` = what shipped inside the portable package (shown only after you updated something, so it differs from current); `latest` = the upstream version, fetched only when you press "check upstream versions". The bundled versions come from `components_bundled.json`, written into the package at build time (it records the runtime and each `tools/` binary). Running from source has no such manifest, so "bundled" simply does not appear. "Latest" is asked of pip itself (`pip index versions`), so the PyPI mirror in Settings applies, and results are cached for 10 minutes; FFmpeg and N_m3u8DL-RE are not on PyPI, so those two rows have no `latest`. When it cannot be determined, the row states why rather than leaving a blank.
- **Auto-check on startup**: three seconds after launch a background thread asks upstream once (it blocks neither startup nor the UI) and caches the result for 10 minutes, so refreshing the same table does not keep asking pip. Only when something really is newer does a reminder pop up — once per browser session; after that the orange dot is left alone and nothing nags you again — and “Settings” in the sidebar gets an orange dot too. Clicking “Go to components & dependencies” in the popup switches to the settings page and scrolls to that card. Two groups are excluded from the judgement: items that are not installed at all (faster-whisper is deliberately not shipped, so counting it would nag about the same thing at every boot), and FFmpeg and N_m3u8DL-RE, which are not on PyPI. The card also has a “Check now” button (it discards the 10-minute cache and really asks upstream) and a switch; with the switch off there is no automatic check and no popup. The change needs “Save settings” and takes effect on the next start. API: `GET` / `POST /api/components/update-check`; `GET /api/components` also returns `auto_check` plus the current check result.
- **Update all**: the first button in the card's button row queues the whole batch at once instead of clicking row by row. It handles "not installed" plus "checked upstream and genuinely newer" — with no version check performed it only fills in what is missing, never guessing at latest versions; a line under the button states in advance which items this run covers. Clicking opens an item-by-item list (`install X (current: not installed)` / `update Y: old → new`); after confirmation it runs **strictly sequentially**, never concurrently (two pip installs would trample each other). Progress and "last batch update: N / M succeeded" show under the button; if faster-whisper is included the models come with it, which can take a while and occupy hundreds of MB. A failure affects only that item and the batch continues, with the source used and the outcome logged per item. Pressing the button while a batch is running says "a batch is already running" and does not queue. If a selected item is not recognized on this machine, the whole batch is rejected on the spot and names the item.
- **How far numpy can go is decided by numba**: librosa depends on numba, and numba caps numpy (`numba 0.65.0` and `0.66.0` both require `numpy < 2.5`; only `0.67.0` onwards allows `< 2.6`). - The whole process is visible in the operation log (which source was used, whether it worked). The running process may still hold the old version in memory; restart to apply.
- The "command-line PATH" block can add `tools/` and `chromaprint/` to your user PATH with one click (user variable only, removable at any time; on macOS / Linux it just prints the export command).

## Notifications

Outbound push through Telegram Bot, WeCom and ServerChan, each with separate finished / failed / subscription switches. Keys are stored only in the local `config.json`, never packaged, never logged. On the browser side there are also desktop notifications, and clicking one jumps to the task it is about. **A notification that could not get out is not simply dropped**: each one is journaled to `notify_outbox.json` first and then sent by a background thread, retried on a 30 s → 2 min → 10 min → 30 min → 1 h backoff that continues after a restart, and the "notification outbox" card in Settings shows who is still owed a delivery and when the next attempt is.

<details>
<summary>Details: the fields and switch keys each channel needs, what clicking a desktop notification does, why the retry journal is on disk, and why a retry never re-sends a message the channel already got</summary>

- **Telegram Bot**: Bot Token and Chat ID, with three independent switches — `telegram_notify_done` / `_fail` / `_sub`.
- **WeCom (企业微信)**: CorpID / Secret / AgentID / touser plus a test send, with the same three tiers `wecom_notify_*`.
- **ServerChan**: a SendKey pushes on download completion; no separate switches for the other tiers.
- **The notification outbox**: a notification used to be "sent once, synchronously, at the moment the event happened" — a momentary outage at the other end, a proxy hiccup, or a restart landing in the wrong second all looked the same from the user's side: "it was supposed to notify me and there was nothing". Now the event is written to `notify_outbox.json` inside the app folder first (**written on enqueue, not only after a successful send**) and a background thread does the sending. A channel that fails is retried at `30 → 120 → 600 → 1800 → 3600` seconds; after the first attempt plus those five retries all fail, the record is marked dropped and the run log names which message it was and why the last attempt failed. The whole timeline is about 1.7 hours. The file is written through a temp file plus `os.replace`, so killing the process mid-write cannot leave a JSON nobody can read back.
  - **A retry only covers what is still owed**: each record tracks its channels individually and crosses one off when it succeeds. If Telegram got it and ServerChan timed out, the next round sends to ServerChan alone — nobody receives the same "download finished" three times.
  - **Which event goes to which channel is still decided by each channel's own switch**; this feature adds no new settings key at all: `_notify_targets()` reads `telegram_notify_{done|fail|sub}` (the "stream went live" kind is not governed by the subscription switch), ServerChan still follows "download finished" only, WeCom reads `wecom_notify_*` (its "subscription" tier defaults to off). With no channel enabled the event is skipped and nothing is written to disk.
  - **Notifications no longer occupy the download thread**: the "download finished" path used to block on Telegram's 15 s plus ServerChan's 15 s plus WeCom's token call and send before the next task could start; now the event is journaled and the worker moves on, while the background thread is kicked immediately so delivery is still normally within a second or two. The Settings card lists what is still owed, how many attempts were made, when the next one is ("2 minutes", not 120) and the last failure reason; "retry now" only pushes pending records to "try immediately" (the request itself does not wait out a 15 s timeout) and "clear" asks first. The two "send test message" buttons still send directly and never enter the retry journal — pressing one means "show me right now", and a test message should not queue ahead of the user's real notifications.
  - When WeCom answers `40014 / 42001 / 41001` (a token that has expired or was never valid) the cached token is dropped, otherwise every retry would bump into the same dead token and the retry mechanism would turn "this recovers in twenty seconds" into "guaranteed to fail for an hour".
  - `notify_outbox.json` records what this machine downloaded, so it sits on the packaging exclusion list next to `config.json` and `history.json` and is never uploaded with the source.
- **Clickable desktop notifications**: the notification shown when a task finishes carries an `onclick` — clicking it switches to the page holding that task (torrent jobs go to the torrents page, everything else to the queue) and flashes that card for 2600 ms. The scroll happens 120 ms after the page switch, because during the page's entry animation a smooth scroll is silently dropped by the browser, so this one is instant. If the task has already been cleared the notification says so and closes itself, rather than leaving a banner that does nothing when clicked.
- All secrets live only in the local `config.json`; they are never packed and never logged.

</details>

## Access protection (login)

This tool used to be "whoever can reach the port is the administrator": the port was bare, with no password at all. **It can now be given a door** — off by default, and even when it is on it only challenges connections arriving from a non-local address: opening it yourself through `127.0.0.1`, the MCP bridge and the browser extension keep working with no login, while anything coming in over the LAN or through a reverse proxy has to pass the login box first. Repeated wrong passwords lock that source out (5 tries → 15 minutes by default), and sessions are measured by idle time (12 hours by default; 30 days when "remember this device" is ticked). The "access protection (login)" card in Settings drives all of it.

<details>
<summary>Details: how "local" is decided, how the password and signing key are stored, why the lockout list is on disk, which doors the machine token opens, and why nothing is enforced when the switch is on but no password exists yet</summary>

- **Source is decided by `request.client.host` alone; `X-Forwarded-For` is deliberately never read**: the same value decides "is this the local machine, does it get to skip the password". Trusting a header would hand the door to anybody who can write one, so anyone reaching the app through a reverse proxy will see the login box — that is intended, not an oversight.
- **Only a salted hash of the password is stored**: PBKDF2-HMAC-SHA256 with 240 000 rounds and a 16-byte random salt, written as one line `pbkdf2_sha256$rounds$salt$derived_key`, compared with `hmac.compare_digest`. No endpoint ever returns the password or its hash, and that key is blank in `GET /api/config`.
- **A session is a signed cookie, not a server-side table**: `mdl_session` carries the version, issue time, last activity and absolute expiry, HMAC-signed with `secret_key`, and is set `HttpOnly` + `SameSite=Lax`. A restart therefore never logs everybody out because "the table was in memory", and it never accumulates sessions nobody cleans up. Idle time beyond `web_auth_session_hours` (12 by default) requires a new login, and the sliding window only re-signs when the cookie is well past the refresh slice; "remember this device" instead follows the absolute `web_auth_remember_days` ceiling (30 by default) and is deliberately not slid.
- **The signing key (SECRET_KEY) is persisted**: generated once as 32 random bytes on first use and written into `config.json`, so **restarting the program does not log browsers out**. Changing the password rotates it, which invalidates every session that is already signed — that is the point: the password may have leaked.
- **Failed attempts and locks live in `login_state.json`**, written through a temp file plus `os.replace`, so killing the process cannot make the app "forget who is locked out" — otherwise every restart would hand a brute-forcer a fresh round. Failures older than an hour stop counting, so one typo is not carried forever. The lock check runs **before** the password is verified, so even the correct password is refused (423) while a source is locked, and the reply says how many seconds are left rather than "correct".
- **The machine token is a second key that only opens data doors**: scripts that cross hosts or a proxy can send `X-MDL-Token`, whose value comes from the "machine token" row in Settings — **generated only by pressing "reset"**; reading an endpoint never generates and writes it as a side effect. It passes the data endpoints (downloads, queue, history) and cannot pass this door itself: `/api/auth/*` never accepts it, and a `POST /api/config` carrying any `web_auth_*` key is a flat 403 — "turn the protection off" is not something a key should be able to do. The MCP bridge only talks to 127.0.0.1, so under this rule it never needs the token; it reads `MEDIADOWNLOADER_MCP_TOKEN` from the environment first and otherwise this local value, so rebinding the app later needs no change to the bridge.
- **Alerts reuse the existing notification channels and add no new switch**: exactly two moments produce a "failed" notification — a source that just got locked, and a source that finally logged in after failing (someone knocked and got in). Ordinary logins stay silent, and a notification problem can never turn the login endpoint into a 500.
- **When the switch is on but no password has been set, nothing is enforced**: at that point nobody could log in, so enforcing it would lock the whole service out of itself. The switch answers 400 until a password exists, and both the card and the status endpoint say plainly that protection is not in effect yet.
- **Five tunables, nothing else**: `web_auth_enabled` / `web_auth_session_hours` / `web_auth_remember_days` / `web_auth_max_fails` / `web_auth_lock_minutes`, all range-checked. The lock list in the UI can unlock one address or all of them; that action has to come from a side that already passes the door (locally it is one click, remotely you must be logged in — the machine token cannot do it).
- `login_state.json` records who has been knocking, so like `config.json` and `notify_outbox.json` it is on the packaging exclusion list and never travels with a shared archive. Self-test: `tests/auth_test.py`, 271 checks (one of them pins that the run log stays 'about the event, never the value': neither the password nor the machine token may appear in it).

</details>

## Themes and language

Run-log lines have their own key / parameter channel: the line written to disk keeps its Chinese bytes unchanged, and the English UI assembles the sentence from the key at display time — lines already in the log are not retro-translated.

## MCP bridge

`mcp_server.py` maps this machine's HTTP endpoints onto MCP tools so an MCP-capable agent can drive the downloader directly. **There is no trace of it in the UI** — it is a command line: start the app first, then run `python mcp_server.py` and let the MCP client spawn it; `python mcp_server.py --tools` prints the mapping without connecting to anything.

<details>
<summary>Details: the tool list is taken from openapi, only loopback is allowed, there is no authentication so do not expose it, and what the call log redacts</summary>

- **The list is not hand-written**: the bridge reads `<BASE>/openapi.json` when it starts, so endpoints added or removed are picked up automatically (this version: of 195 routes, the 194 under `/api/*` other than the front page each become one tool). Query, path and body parameters are flattened into one `inputSchema`, required fields come from the openapi document rather than from guesswork, and endpoints whose body is a free `dict` take a whole `payload`. `/api/events` is a live push stream, so the tool takes the first event and returns instead of blocking on it.
- **Loopback only**: `DEFAULT_BASE` is `http://127.0.0.1:8765`; the port can be changed through an environment variable, but if the host is not `127.0.0.1 / localhost / ::1` the bridge exits immediately — **there is no authentication**, so pointing it at a remote address would expose "change settings, start downloads, delete tasks" unprotected. Loopback addresses bypass the system proxy as well, otherwise talking to your own machine would take a detour and the failure message would be useless.
- **Errors quote the original**: a failed call returns the status code and a summary of the response body; replying only "the call failed" would be no answer at all.
- **Log redaction**: `mcp_calls.log` records which tool was called, the shape of the arguments and the outcome. Any parameter whose name contains `cookie`, `token`, `secret`, `password`, `api_hash` or `key` has its value replaced, and response bodies are never written. Even so, the log still contains endpoint paths, parameter names and queue contents — **do not hand it to someone as a harmless debug file**.
- Its boundaries are the same as [Out of scope by design](#out-of-scope-by-design): the bridge only exposes the endpoints that already exist, and being called by an agent does not add any ability to bypass a login, a payment, DRM or a human check.

</details>

## Common API endpoints

The backend is a single FastAPI file; the full route list is browsable and testable at `/docs`.

<summary>Details: the general endpoints, the torrents endpoints, the subtitle and troubleshooting endpoints, the voice & separation endpoints, and the music-path endpoints</summary>

## Contributing

Single-file backend `server.py` plus single-file front end `static/index.html`; editing `.py` requires a restart. When opening a PR, state the reproduction steps and which self-tests you ran.

<details>
<summary>Details: environment setup, adding a site resolver, self-tests and fixtures, the three places a new dependency must be added, UI and copy rules, re-packaging after document edits, how the default-deny allowlist unignores files</summary>

1. Bring it up: `pip install -r requirements.txt`, then `python server.py`, and open `http://127.0.0.1:8765`. Put ffmpeg / ffprobe / yt-dlp / N_m3u8DL-RE into `tools/`, or install them from Settings.

4. Run the self-tests: `python tests/<name>_test.py` prints PASS/FAIL per assertion and exits 0 when green. `tests/fixtures/` contains four HTML snapshots of public pages (no login content, no cookies) so the offline assertions stay offline.
5. A new dependency must be registered in three places: `requirements.txt`, `PKGS` in `pack_release.py`, and the "Components & dependencies" table (including the `CREDITS` array in the front end; reference projects likewise). A new top-level `.py` module **must** be added to `APP_PY` in `pack_release.py` — omitting it means the packaged app cannot import it. Adding or removing endpoints does not need a second list maintained: both the MCP bridge and the API documentation take their contents from `/openapi.json` at run time, but a request-body model has to be written in a form openapi can generate (`body: SomeBody` without a default value is treated as a query parameter — it neither receives the JSON nor lets `/openapi.json` be generated).
6. ## Privacy

- Everything stays local: `config.json`, `history.json`, cookies and downloaded content all live inside the working directory; the program uploads nothing.
- Logs record actions and errors only — never tokens, secrets, api_hash, passwords, cookie values, SendKey or HLS key contents. Saving settings logs only the changed key names and counts; restoring defaults logs how many keys were restored, their names and the backup file it kept first, and the defaults table always sends an empty string plus a "filled" flag for secret-named keys.
- With "access protection" switched on: the password is stored only as a salted PBKDF2 hash (nobody can read it back), the session is a locally signed cookie, and the signing key plus the machine token are blanked in `GET /api/config` and have no configuration write path at all. Login failure counts and the lock list stay in the local `login_state.json`, never packaged and never logged.
- The "export diagnostics" archive (`POST /api/diagnostics/export`) is meant for **someone else** to read, so redaction happens in the backend: the cookie files themselves, `tg_session/`, downloaded media and the seeding state directory are never included; configuration fields such as `music_platform_cookies`, `musicdl_cookies` and `platform_cookie_content` are stripped wholesale and `meta.json` states how many were hidden; the remaining text passes a second sweep by field name (secrets, tokens, proxy addresses in `user:pass` form); and the `README.txt` inside reminds the recipient to double-check before uploading.
- With "CookieCloud sync" switched on: this is **the only path by which cookies can leave the machine**, and it only ever sends to the address you typed (official hosting, a self-built server or a mirror — your choice), one request per button press, no polling. The sync key stays in the local `config.json`: never echoed in the UI, always blank in `GET /api/config`, never written to the run log or the sync-state file, and even the UUID that requests leaks into its own connection-error text is replaced by `‹UUID›` before that message is stored. Off by default, and while it is off no request is made at all. The state file `cookiecloud_state.json` sits on the packaging exclusion list next to `config.json` and `cookies/`.
- With "Clipboard watch" switched on (`clipboard_watch`, **off by default**): this is the one place where the program proactively reads something another application put on your clipboard, so the rules are explicit — text format only, read only while the switch is on, and the one recognized link is handed only to the local browser over loopback. **The content is never written to the run log and never stored in a state file** (even the pending entry lives in memory and disappears on restart); the same content is asked only once (fingerprints of the last 30 entries, in memory, not on disk), and "Use" merely fills the input box — enqueue and download remain your keystroke. After the switch is off the thread performs zero reads and the status endpoint will not even return a pending link. Turning it on or off logs one line each (the event "the program started watching the clipboard at T", not what it watched).
- The portable archive **excludes all local data by construction**: no `config.json`, no `config.json.bak-<time>` (the copy kept before restoring defaults — the same real settings as `config.json`), no `cookies/`, no `Downloads/`, no `history.json`, `subscriptions.json`, `rss_feeds.json` or `music_favorites.json` (your self-built music list), no `local_index/` (music index snapshots, which contain real local paths), no `tg_session/`, no `torrent_state/` (uploaded torrents, tracker cache and aria2 session files), no `mcp_calls.log` (values are redacted, but endpoint paths and queue contents remain), no `notify_outbox.json` (notifications this machine still owes, which say what it downloaded), no `login_state.json` (failed-login counters and lock list — who has been knocking), no `cookiecloud_state.json` (when the last sync ran and which cookie files it wrote), no `cleanup_state.json` (when the last cleanup pass ran and how much it removed — a record of what this machine deleted), no `browser_sniff_profile/`, and no other local cache or log. A leak scan before packing aborts the build if any of them slipped in.

## Known limitations

What cannot be done is stated in the UI as well; the app never pretends to succeed:

| Limitation | Symptom | Reason |
| --- | --- | --- |
| Range trimming is segmented-stream only | a single mp4 with `download_section` set ignores it, and the task log says so | it rides on yt-dlp's `download_ranges`, which works on HLS segment boundaries |
| No aria2c in the portable package | the first time you press "start download" on the torrents page it answers on the spot what is missing and creates no task | `tools/` inside the archive holds only ffmpeg / ffprobe / yt-dlp / N_m3u8DL-RE, and this whole chain runs on aria2's RPC. **Clicking the aria2 row under "Components & dependencies" installs it now** (into `tools/`), so you no longer have to find a download URL yourself; if you want a specific build you can still drop it into `tools/` or PATH, or point at it under "aria2 & seeding" |
| High-resolution tiers depend on what the site returns | on a risk-controlled egress only 1080p progressive streams resolve, 4K cannot be picked, and the whole row of audio chips disappears | the higher tiers simply are not in the upstream response, and the program does not hide this: the parse card states how many streams came back, the highest resolution, whether they are all progressive, and gives the actionable next steps (cookies / enable PO Token / change egress + update yt-dlp) — when the token is healthy *and* the `all` client has been tried it says "this really is where it stops" instead of staying silent; likewise, when only AVC streams are returned there is no AV1 / VP9 to choose. On the development box this row is backed by readings, and it corrects an earlier call: an A/B run between `default` / `tv` / `web` gave the identical itag set with or without a minted token, which was reported as "the token is not the missing piece" — those clients never spend the token, so the toggled variable was not on the path under test. With `player_client=all` the same video returns **38 streams / up to 4320p / 23 video-only tracks**, and stopping the POT service drops `all` back to 11 / 1080p / zero DASH. **What is needed is the token *and* a client that consumes it**; missing either one keeps high resolution out of the response |
| Trackers and first/last priority affect new tasks only | after changing them you must re-submit; an existing task cannot be moved | aria2's `changeOption` answers "Cannot change option" for `bt-tracker`, and for `seed-ratio` / `bt-prioritize-piece` it answers OK while leaving the value untouched |
| No psutil in the embedded runtime | ending a live recording does not reap the ffmpeg subprocess yt-dlp spawned for the stream, so the file can keep growing and come back after deletion; the backend only logs a warning | this version added it to `requirements.txt` and to the installable list in "Components & dependencies", but did not re-bake the runtime — install it and the problem goes away |
| The non-Windows path is only vouched for by code and offline self-tests | there are no measured readings from an actual Linux / macOS run or from inside a container | the development machine is Windows and has no docker CLI: platform-split tool detection (`is_native_binary` accepts ELF and shebang, rejects `tools/*.exe`), `os.pathsep`-based PATH splitting, `MEDIADOWNLOADER_STATE_DIR`, the `/api/health` probe and the three container files are all pinned by the 44 assertions in `tests/platform_test.py`, but the image has never been built or run |
| The MCP bridge is loopback-only and unauthenticated | the bridge exits immediately if `MEDIADOWNLOADER_BASE_URL`'s host is not `127.0.0.1 / localhost / ::1` | it exposes the 194 endpoints verbatim, including writes such as changing settings, starting downloads and deleting tasks, so it must not be offered as a service |
| The login-state red flag lives until the app closes | a restart or a different egress can bring it back, and "flagged yesterday" will not remind you today | `_LOGIN_FLAGS` is never written to disk — it is a fact about the network right now, not a setting |
| Custom yt-dlp arguments are allowed through a gate | the dangerous items the gate knows (`--exec`, your own cookies, external config, changed failure handling, format selection) are refused by name; **anything not listed is appended verbatim** | yt-dlp's argument surface is wide, and this string is only ever for tasks you download on your own machine |
| The sentence editor and the post-translation checks are in different places | check results only go to the operation log (within `QC_ROWS_CAP=200` lines); to look line by line you still open the editor, and re-running the pipeline overwrites manual edits | the 409 gate only covers "changed after you read it" — the save-then-rerun order is still a human's responsibility |
| The two tables still scroll sideways below 1024 px | on a narrow screen the subscriptions and history tables rely on the container's own scrollbar | `table-layout: fixed` column widths have a floor (the time column and the actions column have to fit the buttons); closing this needs a decision about which column can go |
| YouTube wants cookies | resolution fails or offers only 360p without cookies | the site's "sign in to confirm you're not a bot" wall |
| Douyin search is empty without cookies | classified as login-required / anti-bot challenge / rate-limited / API error / genuinely empty, with the basis shown | the search API returns 200 with the `status_code:2483` login wall, or serves a JS challenge page; this tool does not execute site JS or forge signatures |
| Spotify / Apple have no official audio path | "list titles only + match by title elsewhere", or ~10 s third-party conversions that often fail | DRM; which is why neither is a default match source |
| Quality requirements cannot pin a platform's tier | only ordering, refusal below spec, and post-hoc verification are possible | tiers are hard-coded constants in musicdl's source classes; no client parameter selects quality |
| The lossless reference is metadata only | "Qobuz·ref" rows cannot be selected or downloaded | the audio sits behind a third-party human check; no tokens, no bypass |
| Batch music has a single channel | new songs are not marked read while a previous batch runs; the log says "next scan will catch up" | marking them read would leave them unfetched |
| Title matches are not retried automatically | unmatched rows are marked read and not retried next round | change how the playlist spells that row, or change match sources and press "scan now" |
| Voice stack is not preinstalled | faster-whisper and librosa start as red dots, and so does the whole separation layer (`tools/separator/venv` plus the four RoFormer weights) | the models, torch and environment run to several GB — shipping them means everyone downloads a copy; install from "Components & dependencies" or from the card on the voice page, then restart once |
| The language switch covers the front end | after switching to EN, backend error text, the log lines the backend writes, and the action-name table stay in Chinese | those are on-disk records and the targets of thousands of self-test assertions; a half-translation would leave errors and the interface speaking different languages, so they move in their own batches. The documentation has always been two files |

## FAQ

**Double-clicking `启动.bat` shows nothing happening, or the page never opens.** Read the last line in that window. The program now binds the port itself before starting, and if something holds it the two cases are told apart: whatever answers the health check is **another instance of this program** (its address is printed and you are pointed at it), and only what does not answer is some other process. Both exit with code 1 after writing the same sentence to the run log — it used to be a bare `Errno 10048`, which looked exactly like a hang. A normal start prints its "ready" line only after a background thread actually got an answer from `/api/health`. Changing the port is covered in [What is in the portable package](#what-is-in-the-portable-package).

**The page is sluggish in an external browser the next day, but fine in the built-in one.** This one was not rendering: the six first-screen framework files (Vue, the Element Plus css and main bundle, its zh-cn and en locales, lucide) now ship in `static/vendor/`, so the page fetches nothing from an external CDN and mounts even when the network, a proxy or the CDN itself is dead. Measured before the change, in three states of the same page and server: 214 ms warm cache, 2.3 s cold, and 168 s with the CDN reachable but stalling — six blocking tags waiting 28 s each, serially, with `window.Vue` undefined, 1,332 raw curly braces on screen and no API call made at all. The built-in browser was simply the warm-cache case. Two costs measured and deliberately left alone: `/api/status` takes 1.0–1.3 s because it runs `ffmpeg --version`, imports `yt_dlp` and walks the Whisper directory each time, and the HTML is served `no-store` so it is re-fetched and re-parsed in full.

**Pressing "start download" errors out and no task was created.** That is the dependency preflight (missing yt-dlp / FFmpeg / faster-whisper / N_m3u8DL-RE / telethon, or a download directory you cannot write to). The error names exactly which row of "Settings → Components & dependencies" to install. Cases that merely run slower or lower quality are not blocked.

**YouTube fails, caps at 360p, or a 4K-labelled video resolves to only 1080p.** These are mostly the same thing: the site's risk control wants a logged-in session, and a risk-controlled egress returns only the low-clear HLS renditions and the itag 18 progressive streams — **the higher resolutions simply are not in the upstream response**, it is not that the program truncated the list. The parse card now states plainly "only N streams came back this time, the highest is 1080p, and they are all progressive" and gives the next steps for this machine (add cookies, enable PO Token, change egress, update yt-dlp); see [Cookies & site logins](#cookies--site-logins). Flipping the PO Token switch alone is not enough to get the high tiers: **two things are needed together**. ① The token must be obtainable — that is **bgutil-ytdlp-pot-provider**: its plugin layer installs from one row in "Components & dependencies", and its service layer now ships in `tools/bgutil-pot-server/`, which the program starts with the local `node` whenever the probe finds the port empty (no node binary is bundled, so only a missing `node` on PATH keeps it down). ② The player client must be one that *spends* the token — yt-dlp's `player_client=all` (resolve every client and merge) is that class, while `default` / `web_safari` / `tv` never consume a token, so a perfectly minted token still yields no high tiers through them. Parsing now re-resolves with `all` whenever a list comes back with no video-only track, and the download keeps whatever client produced that list — previously it re-imposed the narrow chain from Settings, `bv*[height<=2160]+ba` found no DASH tracks, the expression fell through to `b[height<=2160]`, and **a 4K pick silently downloaded 1080p progressive while the task still reported "finished"**. The parse card tells you which of the layers (switch / service / plugin) is missing, and the program will not bypass a site's risk control for you. **Only when both of those are in place and the list is still capped does "change the egress" become the right advice**: on the development box the same 4K video with token + `all` gave 38 streams / up to 4320p / 23 video-only tracks (AV1 included), and stopping the node service dropped `all` back to 11 / 1080p / zero DASH. An earlier version of this section claimed the opposite — that A/B compared only clients that never spend the token, so both sides necessarily returned the same itags; the user's "以前那流都不止这些的" turned it around (`Downloads/` held an AV1 7680×4320 file from 2026-10-09). The card states whichever layer is actually short. The same risk control also makes the audio-quality row disappear — a progressive stream carries audio and video together with no separate audio track to choose, which is not a fault.

**Spotify / Apple tracks in a playlist keep coming back "not found".** Check the match sources: the default five resolve addresses fast and download immediately; Spotify and Apple go through a third-party conversion service, which is slow and flaky. When the scoring gate rejects a candidate the log names the dimension (title / artist / duration), and "not searched this round" is reported separately from "not found by title" — the remedies differ.

**I selected a range but got the whole file.** Single-file streams cannot be trimmed; the task log records that the parameter was ignored. Only HLS / m3u8 segmented streams support ranges.

**I asked for audio-only and got no audio file - the queue row still shows a video.** Look first for
`本次未重新下载：… 已在下载记录里` ("not re-downloaded: it is already in the download record") in the run log. That record used to
key on "site + video id" only, **ignoring which kind of output you asked for**, so downloading the video first made a
later audio-only request count as done. Audio-only now keeps its own record (`download_archive_audio.txt`), and
"Clear download records" in Settings clears both files.

**"Skip already downloaded" is on and it still re-downloaded that song.** The per-row "download" button is an explicit single action and is not bound by that checkbox. Also, four cases never block: the template contains `{id}` or `{source}`, no title is available, the target directory does not exist yet, or the directory holds only sidecar files (`.lrc`, covers).

**Audio analysis fails with `Numba needs NumPy 2.4 or less. Got NumPy 2.5.`** numba caps numpy, and numba has no row in the components table: either move both forward with `pip install numba==0.68.0 llvmlite==0.50.0` (`0.67.0` onwards allows `numpy < 2.6`), or roll numpy back to 2.4.x / leave it out of the batch. The error comes from `import numba`, so audio analysis and voiceprint diarization break together.

**The torrents page answers an error as soon as I press "start download", or repeats "读 aria2 活动任务失败: … WinError 10061" every 30 seconds.** That page runs entirely on aria2: with no aria2c installed (it is not in the portable package) or no reachable RPC, it says exactly what is missing and creates no task; that 10061 just means "nobody is answering on port 6800", most often because this machine has no aria2c at all. When it is missing you now fix it by clicking the aria2 row's "install" under "Components & dependencies" (it fetches `tools/aria2c.exe` and starts it on the spot); if you want a specific build you can still drop it into `tools/` or PATH, or point at it under "aria2 & seeding". The "check aria2" button now actually starts the process, and with "auto-start aria2" on (the default) the program launches one listening on 127.0.0.1 only. The error text goes through `aria2_err_cn()`, rewritten into a next step you can act on rather than a raw urllib message.

**A live recording runs on and on and the file keeps getting bigger.** To have it stop and save on its own after a set time, fill in the minutes next to "开始录制" (start recording) on the live page (0 = follow the "直播默认最长录制" default in Settings); the sessions a monitor starts automatically use each room's own setting. A recording you started by hand had no length to hang on before — it only stopped when someone pressed "结束录制" (stop recording) — but it now honours the same three-level precedence, and when the limit is reached it ends on its own and runs the full save path. A streaming subprocess that cannot be reaped is a different matter — see the psutil note below.

**A magnet has sat there a long time with no file list.** The torrent metadata has to arrive before the program can know what is inside; `torrent_meta_timeout` (default 180 s) expiring means nobody is seeding right now — it is not a malformed link.

**A live recording keeps growing after I stopped it, and comes back after deletion.** The embedded runtime in the portable package has no psutil, so the ffmpeg subprocess yt-dlp spawned for the stream is not reaped. Install psutil from "Components & dependencies", or confirm that process yourself.

**Saving in the sentence editor says the subtitle was rewritten.** That is the 409 gate: after you read the file, the pipeline (or another window) changed it, so the write is refused rather than overwriting freshly generated content. Re-read as prompted and edit again; a `原名.bak-<timestamp>` backup is taken in the same directory before every save anyway.

**The MCP bridge does not start / says it cannot get openapi.** It does not serve on its own — `server.py` has to be running first (default `http://127.0.0.1:8765`, change the port through the environment variable). Pointing `MEDIADOWNLOADER_BASE_URL` at a non-loopback address is rejected on purpose: this bridge has no authentication.

**Someone needs to help me debug.** Press "export diagnostics" on the log page: the zip contains the version and runtime environment, status, component table, queue, redacted configuration and recent logs. Cookies, sessions, downloaded media and the seeding state directory are not in it, and `meta.json` lists the exclusions item by item.

**Two startup log lines about SSL library / cryptg not installed.** telethon has fallen back to pure-Python crypto and Telegram operations will be slow. The portable package from v1.2.8 onwards bundles cryptg; from source, just install it.

**Fingerprint lookup reports `invalid API key`.** That field wants the acoustid.org **application** client key, not the user API key shown after you log in.

**I installed dependencies but nothing changed.** The running process still holds the old version in memory — restart (`python server.py`, or relaunch `启动.bat`). Front-end-only changes in `static/index.html` just need a page reload.

**Where is the log file?** The "log" page states its location at the top — it is in the program folder — and opens it with one click. Files rotate daily and are deleted after 7 days.

## Out of scope by design

These are deliberate omissions, not a backlog:

- No bypassing login walls, paywalls, DRM or any human-verification challenge (Turnstile / CAPTCHA); no obtaining or forging verification tokens.
- No executing a site's challenge JavaScript and no forging its anti-bot signature.
- Telegram channels with "restrict saving content" are an explicit no-save signal and are not worked around; login is api_id / api_hash plus phone code and 2FA only — no QR sign-in.
- The Qobuz / Tidal lossless reference reads metadata only; not a byte of audio is fetched.
- HLS keys pushed by cat-catch are only the ones you already captured yourself; the program never goes looking for or breaks one.
- Custom yt-dlp arguments are deliberately not an entry point for executing commands: items the gate recognises as dangerous (`--exec`, which runs an arbitrary command after a download) are refused by name, and the MCP bridge stays on loopback instead of being offered as a service.
